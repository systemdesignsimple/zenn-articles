同じデータの2つのコピーの間のネットワークが切れると、片側での書き込みがもう片側に届かなくなります。そうなると各側は、最新であることを証明できないリクエストを断るか、間違っているかもしれないコピーから答えるか、どちらかを選ばなければなりません。CAP定理が言っているのは、回線が切れたままでデータが変わり続ける間は、どの設計もこの選択から逃れられないということです。面接でよく聞かれる質問が、まさにこれです。CAPとは何か、銀行ならCPとAPのどちらを選ぶか。


## 前提知識
**レプリケーション。**同じデータのコピーを複数のサーバーに置くこと。サーバーが1台失われてもデータが残り、ユーザーに近い場所から読めます。すべての書き込みは他のコピーまで届かなければならず、それには時間がかかります。その影響は[1つのデータベースが書き込み、10が読む: レプリケーション遅延](https://systemdesignsimple.com/one-database-writes-ten-read/)で測りました。CAPはその極端な場合です。届くはずの旅が、経路が壊れたせいで決して終わらないのです。

**2人の書き手、1つの値。**2つのリクエストが同時に同じものを変えようとすると、どこか1か所が順序を決めなければ、両方が勝ってしまいます。[2人のファンが1席を争う](https://systemdesignsimple.com/two-fans-one-seat/)では、チェックと確保を1つの原子的なステップで行うことで直しました。「残高は足りるか」と確認する2件の引き出しは、別々のコピーを見れば両方とも通ってしまいます。

**数値としての可用性。**サービスがリクエストに答える割合です。コピーを横に並べると上がります。[2台を直列に並べると2倍壊れやすい](https://systemdesignsimple.com/two-servers-in-a-row/)で見た通りです。[99.9%でも年間8時間は止まる](https://systemdesignsimple.com/three-nines-8-hours-down/)では、パーセントを時間に直しました。CAPが使う可用性は、もっと厳しい、イエスかノーかの意味です。定義はこの後です。

## 用語の定義
**ネットワーク分断**: 一部のサーバー(ノード)の間でメッセージが失われ、互いに聞こえなくなったグループに分かれる状態。各グループは自分のクライアントの声は聞こえ続けます。海底ケーブルが切れるのが教科書の絵です。

**線形化可能性(CAPのC)**: すべての操作が、開始と終了の間のどこか一瞬に起きたかのように見え、あたかもコピーが1つだけあるかのように振る舞い、その順序が実時間を守ること。書き込みが終わった後に始まった読み取りは、その書き込みか、それより後の書き込みを見なければなりません。書き込みと重なった読み取りは、古い値でも新しい値でもかまいません。

**可用性(CAPのA)**: 故障していないノードに届いたすべてのリクエストが、最終的にエラーでない応答を得ること。「後で試してください」はエラー応答なので、そう言うノードは可用ではありません。

**分断耐性(CAPのP)**: ノード間のネットワークがメッセージを失っても、システムが動き続けること。実際には、分断中に何をするか決めてあるという意味です。分断は防げないのですから。

**クォーラム(過半数)**: 投票メンバーの半分より多い数。3票のうち2票がクォーラムです。同じグループの過半数は、どれも少なくとも1人のメンバーを共有します。だから分断した片側だけが過半数を持てるのです。

**古い読み取り**: 最新の完了した書き込みよりも古い値を返す読み取り。私たちのラボでは、その時点の台帳と残高が合わない読み取りを「不一致の読み取り」と呼びます。

**Last-writer-wins(LWW)**: 衝突の解決ルールで、タイムスタンプが最新の値を残し、もう一方を黙って捨てます。

**不変条件**: 「残高がゼロを下回らない」のような、データについて常に守らなければならないルール。レプリケーションのプロトコルではなく、アプリケーションのものです。

## 仕組み: CAPが実際に言っていること
![ヨーロッパとアジアのサーバーラックがデータのレールでつながり、真ん中で切れて LINK CUT のラベルと火花が見える](https://systemdesignsimple.com/img/cable-to-asia-breaks/b01.webp)
*動画の導入: 1つの口座の2つのコピーと、その間の切れたリンク。*

Eric Brewerがこのアイデアを予想として述べたのは2000年、Seth GilbertとNancy Lynchが正確な形で証明したのは2002年です。ていねいに言うとこうなります。メッセージが失われる非同期ネットワークでは、分断が続いて値が変わり続ける間、どのシステムも線形化可能な読み取りと、動いているすべてのノードからの答えの両方を保証できません。

証明は頭の中で追えるほど短いです。1つの値を2つのノードG1とG2に置き、その間のメッセージをすべて切ります。クライアントがG1に新しい値を書き込みます。システムが可用なら、G1はG2を待たずに書き込みを受け入れて返事をしなければなりません。待つのは永遠に続くかもしれないからです。次に別のクライアントがG2から読み取ります。やはり可用性が言うのは、G2は答えなければならないということです。でもG2は書き込みのことを一度も聞いていません。古い値を返します。書き込みは読み取りが始まる前に終わっていたので、線形化可能性は新しい値を要求します。両方の約束は同時には守れません。逃げ道は、G1が書き込みを断るか、G2が読み取りを断るかしかありません。断ることは可用性をあきらめることです。

この定理が当てはまるのは分断している間だけです。メッセージが流れている間は、システムは整合性も可用性も両方持てます。データが変わらない間も当てはまりません。切断中に誰も書き込まなければ、すべてのコピーは今も最新だからです。

だから「3つのうち2つを選ぶ」は誤解を招きます。Pは外せません。ネットワークの故障を外すことはできないからです。「CAだ」と言う設計は、ノードが1つしかない(冗長性がない)か、回線が切れたときに何をするか言っていないかのどちらかです。Brewerの2012年の記事も同じことを言っています。選択が生じるのは分断している間だけで、良い設計は分断を検知し、操作ごとに選び、回復の計画を立てます。

だから複製されたストアについては、こう問うべきです。コピー同士が話せない間、どの操作が断られ、どの操作が遅れているかもしれないコピーから答えるのか。

## 分断中、CPシステムは何をするか
CPシステムは、最新であることを証明できない側の可用性をあきらめます。どちらがその側かは、ふつう過半数の投票で決めます。Raft(etcd)やZAB(ZooKeeper)のような合意プロトコルで作られたシステムは、投票者の過半数が保存してからでないと書き込みを受け入れません。過半数を持つ側だけがリーダーを選んで書き込みを続けられます。

読み取りも同じ注意が必要です。少数派の側がローカルのコピーから読み取りに応じると、過半数側がすでに置き換えた値を渡してしまいます。まさに証明で見た通りです。だから線形化可能な読み取りは、過半数に確認するか、自分が今もリーダーだと確信しているリーダーに任せなければなりません。etcdはデフォルトでそうします。別に、ローカルのメンバーから古いデータを返すかもしれない「serializable」読み取りの選択肢もあります。ZooKeeperは逆がデフォルトです。ふつうの読み取りは、つながっているサーバーから出され、古いことがあります。読み取りの前に`sync`を呼ぶと、そのサーバーの見え方を最新に近づけられますが、最新の値を厳密に保証するわけではありません。`sync`はクォーラム操作ではないからです([ZooKeeper internals](https://zookeeper.apache.org/doc/r3.8.4/zookeeperInternals.html#sc_consistency))。

![実行1 CP: ヨーロッパが証人と合わせて3票のうち2票を持ち、資金をチェックして支払い、アジアは TRY LATER を示す。CPレーンはヨーロッパの300を読み取る](https://systemdesignsimple.com/img/cable-to-asia-breaks/b03.webp)
*実行1、CP: ヨーロッパが3票のうち2票を持って支払います。アジアは自分のコピーが最新だと証明できず、「後で試してください」と言います。*

私たちのラボは、実際の合意プロトコルなしにこれをモデル化しています。票は3つあります。ヨーロッパのレプリカ、アジアのレプリカ、そしてヨーロッパにある証人(データはほとんど持たず、同数を割る投票者)です。切断中、ヨーロッパは3票のうち2票を持ってサービスを続けます。アジアは3票のうち1票しか持たないので、読み取りも含めてすべて断ります。自分の残高が最新だと証明できないからです。

クライアントは各リクエストをコイントスでヨーロッパかアジアに送ります。20秒の切断中、442件のうち224件がアジアに着いたので、CPは224 / 442 = 50.7%を拒否しました。ヨーロッパが残りの218件に応じ、その読み取りはどれも台帳と違いませんでした。修復のとき、アジアはヨーロッパのログから欠けていた操作を再生し、両側は760で一致しました。

証人をどこに置くかが、どちらのユーザーがエラーを見るかを決めます。3つ目の地域に置けば、証人とつながり続ける側が勝ちます。決め手がなければ、どちらの半分も過半数を持てず、CPは両側で書き込みを断らなければなりません。過半数をどこに置くかは、プロダクトの判断です。

## APシステムは何をし、どう修復するか
APシステムは、動いているすべてのノードが自分のコピーから答え続け、回線が戻るまでコピーがずれていくのを許します。各側は自分の書き込みを記録します。分断が直ると、両側は見逃した分を交換し、衝突を調整します。

Apache Cassandraはリクエストごとに選べます。整合性レベル`ONE`では、読み取りも書き込みもレプリカ1つで足りるので、そのデータのレプリカに届く限り、分断のどちら側でも動き続けられます。`QUORUM`では、そのデータのレプリカの過半数が必要で、少数派の側では失敗します。レプリカが食い違うと、Cassandraはタイムスタンプが最新の書き込みを残します。こうしたレベルは、応答しなければならないレプリカの数を変えますが、`QUORUM`だけではCAPの整合性は保証されません。Cassandraは、Paxosを使う軽量トランザクションによる線形化可能な条件付き操作を提供しています([Cassandra guarantees](https://cassandra.apache.org/doc/latest/cassandra/architecture/guarantees.html))。

![実行2 AP: 各側が自分のコピーを持ち、両方とも引き出しを支払う。APレーンはヨーロッパ300、アジア300、台帳は赤字で-400を示す](https://systemdesignsimple.com/img/cable-to-asia-breaks/b04.webp)
*実行2、AP: 各側が自分のコピーを信じて支払います。各コピーは300を示しますが、合わせた台帳は-400です。*

私たちのラボでは、APは切断中の442件すべて、100%に応答しました。その代償は答えのほうに来ました。両側が書き込んでからは、各コピーは相手の変更を知らないので、ほぼすべての読み取りが台帳と合わない残高を示しました。241件の読み取りが不一致でした。各側は自分のコピーで資金をチェックしたので、700のスクリプト引き出しは両方とも通り、合わせた残高が足りない間の小さな引き出しも通りました。APは、台帳に資金がないのに15件の引き出しを受け入れ、台帳は-135まで落ちました。CPの台帳は584を下回りませんでした。

別に、コピーが1つで切断のない直列の参照銀行も、同じ流れを時間順に、自分の判断で実行しました。APが受け入れた引き出しのうち、拒否したのは1件だけです。アジアの700です(これはラボのローカルコピーに追加の出力で確認しました。公開されているrun.mjsは件数だけを出力します)。残りの14件は小さなもので、直列の銀行もその700を断った後もまだお金があったので支払いました。APは、合わせた帳簿が赤字の間にそれらを受け入れました。

修復のステップが、次に何を失うかを決めます。ラボではAPを2つの修復ルールで2回実行しました。

- ログのマージ: 両方のレプリカのログを操作idで組み合わせ、時間順に並べ、開始残高から再生するので、受け入れられた操作はすべて1回だけ数えられます。残高は台帳と一致しました。誤差0です。使いすぎは残ります。お金は本当に出ていったのですから。マージがするのは、帳簿を正直にすることだけです。
- 残高に対するlast-writer-wins: 最後に書いたレプリカがもう一方を上書きします。ヨーロッパが最後に書いたので、その760がアジアのコピーを置き換え、アジアの切断中の94件の書き込みが消えました。台帳は92と言いました。760 - 92 = 668ずれています。誤差は残りました。修復後の223件の読み取りがずれ、実行は803で終わり、台帳は135でした(668のずれ)。

668は、アジアの書き込みからそのまま出てきます。両側とも切断の開始時は1336でした(CPの凍ったアジアは、修復の時点でも1336を示していました)。アジアの書き込みが自分のコピーを668まで動かしました。純粋な変化は668 - 1336 = -668、668の減少です。LWWはその減少を捨てたので、修復後の残高を668多く見積もってしまいました。LWWは803でも終わりました。CPと同じです。その帳簿は、アジアがすべてを断ったかのように見えます。でもアジアは支払ったのです。システムはそれを忘れました。

![ラボのターミナルの出力: 切断中442件、CPは50.7%を拒否、CPの不一致の読み取り0、APは100%に応答、APの不一致の読み取り241](https://systemdesignsimple.com/img/cable-to-asia-breaks/b05.webp)
*実際のラボの出力: 切断中の同じ442件が、拒否されたか、ずれたか。*

台帳は、ラボが自分で持っている、どのレプリカが受け入れた操作もすべて時間順に記録したものです。どのレプリカも台帳を読みませんし、どの修復も台帳を使いません。本当に出入りしたお金の物差しでしかありません。台帳と違う読み取りが0件なのは良い兆候ですが、CPが線形化可能だという証明にはなりません。ラボはレプリケーションが瞬時で、時計も完璧です。線形化可能性のチェッカーは、Jepsenの分析の裏にあるもののように、記録された履歴が実時間を守る合法的な逐次順序を少なくとも1つ許すかどうかをテストします。1つの履歴をチェックして通るのと、実装が正しいことを証明するのとは別です。証明には、あり得るすべての履歴について考える必要があります。

## 整合性があれば使いすぎを防げるか
いいえ。これがCAPについて最も多い誤解です。線形化可能性が言うのは、操作が1つのコピーの上にあるかのように、実時間の順序で振る舞うということだけです。どの操作が許されるかについては何も言いません。線形化可能なストアでも、アプリケーションが「残高 = 残高 - 700」とチェックなしに2回書き込めば、残高は-400になります。

「ゼロを下回らない」は、アプリケーションが守らなければならない不変条件です。ふつうは、チェックと変更を1つの原子的なステップで行います。Part 2の席と同じです。多くのストアが条件付き書き込みを用意しています。DynamoDBでは、書き込みに条件式を付けられ、条件が偽なら失敗します。SQLでは`UPDATE ... WHERE balance >= 700`で、変わった行の数を報告します。

```sql
-- debit.sql: 最新の1つのコピー上で、チェックと支払いを1つの原子的なステップで
UPDATE accounts
SET    balance = balance - 700
WHERE  id = 42 AND balance >= 700;
-- 1行更新された = 支払った
-- 0行更新された = お金が足りない、断る
```

CPは、分断している間もこのステップを意味のあるものにします。チェックが、受け入れられたすべての書き込みを持つコピーで実行されるからです。私たちのラボでは両方のモードが同じ資金チェックを実行しました。違うのは、APは相手側の引き出しが欠けたコピーでチェックを実行したことです。

Brewerの2012年の記事は、もう一つの道を説明しています。分断している間は操作を通し、記録し、回復のときに壊れた不変条件を検知して補償するのです。彼の例は現金自動預け払い機です。切断中も上限付きで引き出しを許し、あとで精算します。やり方は、リスクに上限を付け、受け入れた操作をすべて記録し、帳簿が赤字になったときの修正方法を決めておくことです。そのためにはマージされたログが必要です。last-writer-winsは証拠を消してしまいます。

## CAPが言っていないこと
CAPは狭い定理で、証明する範囲を超えて引き伸ばされることが多いです。

- データベース全体のラベルではありません。多くのストアはリクエストごとに選べるので、1つのシステムが残高にはCP、プロフィール写真にはAP、ということもできます。
- そのCはACIDのCではありません。ACIDの整合性は、トランザクションがアプリケーションのルールを守ること、つまり上で見た不変条件に近いものです。CAPのCは線形化可能性です。
- そのAは稼働率より厳しいものです。少数派の側で20秒間リクエストを断るCPシステムは、CAPの可用性では失格でも、99.9%のサービス目標は満たせます。
- レイテンシについては何も言いません。合意にはクォーラムとの通信が必要なので、必要な過半数が大陸をまたぐ場合、分断がなくてもすべての書き込みが大陸間の往復を待ちます。PACELCがこれを足します。分断していればAかC、そうでなければレイテンシか整合性、です。帯域を増やしても、その待ち時間は短くなりません。[10車線でも遅い](https://systemdesignsimple.com/ten-lanes-still-slow/)で、レイテンシとスループットの違いとして見ました。
- 多くのシステムはどちらでもありません。非同期のフォロワーを持つ単一のリーダーは、線形化可能でも(フォロワーが遅れる)完全な可用性でもありません(少数派は書き込めない)。

だから選択は、データの1つ1つに属します。このシリーズのPart 8では、なぜいいねの数は間違っていても、残高は決して間違わないのかを問います。

*CとAとP。ケーブルが切れている間は、CかAのどちらか、両方ではありません。*

## 具体例
動画では、1つの共有口座と、同じ瞬間の2件の引き出しを使います。ここの数字は具体例で、概念だけのものです。ラボのスクリプトされた700は通常のトラフィックと一緒に起きるので、ラボ自身の数字とは違います。

```text
前提: 1つの口座、開始残高1000、コピーはヨーロッパとアジア、回線は切断。
ヨーロッパのクライアントとアジアのクライアントが、同じ瞬間にそれぞれ700を頼む。

CP(証人の票はヨーロッパにあるので、ヨーロッパが3票のうち2票を持つ)
  ヨーロッパ: 1000 >= 700 を確認、支払う   ヨーロッパのコピー = 1000 - 700 = 300
  アジア:   3票のうち1票、過半数なし      「後で試してください」
  支払った合計700、帳簿300、赤字なし

AP(各側が自分のコピーを信じる)
  ヨーロッパ: 1000 >= 700 を確認、支払う   ヨーロッパのコピー = 300
  アジア:   1000 >= 700 を確認、支払う   アジアのコピー   = 300
  支払った合計700 + 700 = 1400
  合わせた台帳 = 1000 - 1400 = -400(各コピーはまだ300を示す)
```

そして測った版です。私たちのラボから(labs/sd-7、シード7、1台のApple M2 Pro、Node v22.13.1、シミュレーションの時計)。前提: 60秒のシミュレーションを秒間約20リクエスト、両側に均等に分ける。50%が読み取り、25%が入金、25%が5から25の引き出し。30秒時点で各側に1件ずつスクリプトされた700。切断は20秒から40秒まで。すべてのモードが、金額も含めてまったく同じリクエストの流れを受けます。

```text
リクエスト          切断前398  切断中442  切断後398  (合計1238)

切断中                                  CP             AP(修復まではマージもLWWも同じ)
  応じた                                218 (49.3%)    442 (100%)
  拒否した                              224 (50.7%)    0
  不一致の読み取り                      0              241
  台帳に資金がないのに受け入れた引き出し  0              15
  直列の銀行が断った引き出し            0              1
  台帳の最低残高                        584            -135

修復時(20秒から40秒の書き込み: APではヨーロッパ105件、アジア94件。CPではアジア0件)
  CP        ヨーロッパ760、アジア1336 -> 再生 -> 760、台帳760、誤差0
  AP-マージ ヨーロッパ760、アジア668  -> マージ ->  92、台帳 92、誤差0
  AP-LWW    ヨーロッパ760、アジア668  -> ヨーロッパが勝ち、94件の書き込みが消える

            修復後: 223件の読み取りがずれる。最後は803に対して台帳135(668のずれ)
```

CPは少数派の側のトラフィックをエラーに変え、帳簿を正しく保ちます。APは答え続け、その代わりに不一致の読み取り、使いすぎ、デリケートな修復を払います。「約半分が拒否された」が成り立つのは、トラフィックが均等に分かれ、過半数が片側にあったからです。

## コード
このPythonスクリプトは、1000 / 700 / 700の例を両方のモードで再現し、APの実行を2通りの方法で修復します。標準ライブラリだけです。`python3 cap_toy.py`で実行してください。

```python
# cap_toy.py: 1つの口座、2つのコピー、切れた回線、700の引き出し2件(CPとAP)
START = 1000
REQUESTS = [("Europe", 700), ("Asia", 700)]   # 同じ瞬間、回線はすでに切断
VOTES = {"Europe": 2, "Asia": 1}               # 証人の票はヨーロッパにある
MAJORITY = 2                                   # 3票のうち2票

def run(mode):
    copy = {"Europe": START, "Asia": START}    # 各側の自分の残高
    log = {"Europe": [], "Asia": []}           # 各側の受け入れた操作
    ledger = START                             # 私たちの物差し: 受け入れたすべての操作
    for t, (side, amount) in enumerate(REQUESTS):
        if mode == "CP" and VOTES[side] < MAJORITY:
            print(f"  {side:6} -{amount}: try later (cannot reach a majority)")
            continue
        if copy[side] < amount:                # チェックと支払いを1つのステップで、このコピー上で
            print(f"  {side:6} -{amount}: declined, not enough money")
            continue
        copy[side] -= amount                   # 回線が切れているので、もう片方のコピーは決して聞かない
        log[side].append((t, -amount))
        ledger -= amount
        print(f"  {side:6} -{amount}: paid, this copy now shows {copy[side]}")
    print(f"  copies show {copy}, ledger of accepted operations {ledger}")
    return copy, log, ledger

def repair_merge(log):
    ops = sorted(log["Europe"] + log["Asia"])  # 両方のログの和集合、時間順
    return START + sum(delta for _, delta in ops)

def repair_lww(copy, log):
    last = {s: (log[s][-1][0] if log[s] else -1) for s in copy}
    winner = max(copy, key=lambda s: last[s])  # 最後に書いた側が残高を保つ
    return winner, copy[winner]

print("CP (refuse rather than guess):")
run("CP")
print("AP (answer from the local copy):")
copy, log, ledger = run("AP")
print(f"  repair by merging logs: balance {repair_merge(log)} (matches the ledger, still overdrawn)")
winner, bal = repair_lww(copy, log)
print(f"  repair by last-writer-wins: {winner} wins, balance {bal}, ledger {ledger}, off by {bal - ledger}")
```

実行して観察すること:

```text
CP (refuse rather than guess):
  Europe -700: paid, this copy now shows 300
  Asia   -700: try later (cannot reach a majority)
  copies show {'Europe': 300, 'Asia': 1000}, ledger of accepted operations 300
AP (answer from the local copy):
  Europe -700: paid, this copy now shows 300
  Asia   -700: paid, this copy now shows 300
  copies show {'Europe': 300, 'Asia': 300}, ledger of accepted operations -400
  repair by merging logs: balance -400 (matches the ledger, still overdrawn)
  repair by last-writer-wins: Asia wins, balance 300, ledger -400, off by 700
```

3つの変更を試してください。`VOTES = {"Europe": 1, "Asia": 2}`にすると、ヨーロッパが「後で試してください」と言う側になります。両方を1にすると、CPは両方の引き出しを断ります。APで2つ目のリクエストを200にすると、両方とも支払い、台帳は100で終わり、赤字にはなりません。だから金額に上限があれば、APでも受け入れられるのです。フルラボ(`node labs/sd-7/run.mjs`)は、同じ考えを読み取りと入金も含む流れ全体で実行します。

## 失敗モードと端のケース
**分断と遅いノードは区別できません。**ノードが見えるのは、返事が止まったことだけです。相手は死んでいるのか、過負荷なのか、切断されているのか分かりません。だから分断はタイムアウトで検知します。タイムアウトは推測です。短すぎると、忙しい一瞬で不要なリーダー選挙が起きます。長すぎると、ユーザーが待ちます。選挙の回数を見てください。増え続けていれば、実際のレイテンシに対してタイムアウトがきつすぎることが多いです。

**スプリットブレイン。**2つのノードが両方とも自分がリーダーだと思い込み、両方とも書き込みを受け入れます。典型的なのは2ノードのフェイルオーバーペアで、相手が見えなくなると各側が自分を昇格させる場合です。直し方は、本物のクォーラム(奇数の投票者か証人)とフェンシングです。リーダーの任期やトークンをストレージがチェックし、古いリーダーの書き込みを拒否します。

**退任したリーダーが読み取りに応じる。**少数派に切り離されたリーダーは、しばらくの間自分がまだリーダーだと思い込み、新しいリーダーがすでに変えた値を出してしまうことがあります。合意システムは、答える前に過半数でリーダーシップを確認するか、時計のずれに上限があることを前提にしたリースを使います。「速いローカル読み取り」をオンにすることは、そのリクエストでは古い読み取りを選ぶことです。

**部分的・一方的な分断。**AはBに届き、BはCに届くのに、AはCに届かない。あるいはメッセージが一方向にしか流れない。こうした分断は、タイムアウトや障害検知のバグをあぶり出します。ノード全体を落とすだけでなく、特定のペアの間のトラフィックを落とすフォールトインジェクションでテストしてください。

**last-writer-winsでの時計のずれ。**LWWは、別々のマシンのタイムスタンプを信じます。あるサイトの時計が進んでいれば、その書き込みは実際には早かったのに勝ってしまいます。私たちのラボは時計が完璧なので、実際のLWWはもっと失うことがあります。すべての操作を残すマージか、キーごとに1つのホームコピーを選んでください。

**分断中のリトライ。**「後で試してください」と言われたクライアントは、別の場所でリトライするかもしれません。タイムアウトしたリクエストは、実は成功していたかもしれません。書き込みごとに一意のidがなければ、リトライされた引き出しは、ログがマージされたときに2回支払われます。すべての書き込みにidを付け、ラボのマージが操作idで行うように重複を除いてください。

## よくある間違い
**間違い:** 「CAを選びました」。 **代わりに:** ネットワークが分断したときに何が起きるか言ってください。分断は選べるものではないので、本当の選択は、分断中のCかAです。

**間違い:** CAPのCをACIDのCと同じだと思うこと。「使いすぎなし」と同じだと思うこと。 **代わりに:** Cは線形化可能性です。不変条件は別に守ります。最新の1つのコピー上で、チェックと変更を1つの原子的なステップで行います。

**間違い:** CP設計で少数派の側に「読み取りだけなら」と応じさせること。 **代わりに:** その読み取りは古いことがあります。断るか、古い可能性があると明記して、それでかまう場面だけに使います。

**間違い:** 残高のように足し合わせる値を、last-writer-winsで修復すること。 **代わりに:** 操作ログをマージする(idで重複を除く)か、両側の変更を組み合わせるデータ型を使います。

**間違い:** データベース全体にCPやAPのラベルを貼って、そこで止まること。 **代わりに:** 各リクエストが使う設定(読み取りと書き込みのレベル、読み取りの選択肢)と、少数派の側での振る舞いを確認します。

## 面接で聞かれたら
1. **確認:** どのデータがサイトをまたいで複製され、どの操作は絶対に間違ってはいけないか(残高、在庫)と、どれが少し古くてもいいか(いいね、表示回数)。
2. **前提:** サイトを述べ、分断はいつか起きると言い、強い整合性が必要なものには過半数クォーラムを前提とする。
3. **構造:** レプリカと投票者を描き、過半数がどこにあるかを示し、分断中にどちら側が断るか言う。
4. **深掘り:** Cを線形化可能性、Aを動いているすべてのノードからの答えとして定義する。分断中と修復時に、読み取りと書き込みが各側で何をするか歩く。
5. **トレードオフ:** CPは少数派の側でのエラーと、クォーラムが地域をまたぐときの大陸間のレイテンシがコスト。APは古い読み取り、壊れた不変条件、ていねいなマージがコスト。
6. **まとめ:** 操作ごとに選ぶ。残高には原子的な資金チェック付きのCP。カウンターとフィードにはマージ付きのAP。そしてテスト済みの回復計画。

**60秒で答えるなら**

CAPが言うのは、レプリカの間のネットワークが分断してデータが変わり続ける間は、線形化可能な読み取り、つまりシステムが実時間の順序で1つのコピーのように振る舞うことと、動いているすべてのノードからのエラーでない答えの両方を保証できない、ということです。分断はいつか起きるので、本当の判断はその間のCかAです。銀行の残高ならCPを選びます。過半数クォーラムで、過半数の側がサービスを続け、少数派の側は推測するより「後で試してください」と言います。さらに原子的なチェックと引き落としを付けます。整合性だけでは使いすぎを防げないからです。20秒の切断のシミュレーションでは、CPは約半数のリクエストを断り、不一致の読み取りは0件でした。APはすべてに応答しましたが、241件の読み取りが不一致で、帳簿は赤字になりました。いいねや表示回数ならAPを選び、分割の後に数をマージします。

## 練習問題

**[初級] CとAとPは、正確には何の略ですか?**

C: 線形化可能性。操作が1つのコピーのように、実時間の順序で振る舞うこと。A: 故障していないノードへのすべてのリクエストがエラーでない答えを得ること。P: ノード間のメッセージが失われてもシステムが動き続けること。

**[初級] なぜ「3つのうち2つを選ぶ」は誤解を招くのですか?**

分断から逃れることはできないからです。CとAの選択が生じるのは分断が続いている間だけで、分断の外ではシステムは両方持てます。

**[中級] 投票者が5人いて、3対2に分かれました。過半数クォーラムのシステムでは、どちら側が書き込みを確定できますか。もう一方の側の読み取りはどうなりますか?**

3人の側が過半数(5人の半分より多い)を持ち、書き込みを確定し続けます。2人の側はできません。そこでの線形化可能な読み取りも失敗しなければならず、さもなければ過半数が置き換えた値を返す危険があります。

**[中級] ラボでは、なぜCPは50%ではなく50.7%を拒否したのですか?**

リクエストがコイントスで各側に送られ、切断中の442件のうち224件が少数派のアジアに着いたからです。224 / 442 = 50.7%です。

**[中級] 線形化可能なストアに残高1000があります。2人のクライアントがそれぞれ「残高を読み、700引いた残高を書く」を2つの別々の操作として実行します。まずくなりますか?**

はい。両方の読み取りが書き込みの前に1000を返すことがあり、両方の書き込みが成功して、1000から1400が支払われます。各操作は線形化可能です。不変条件には1つの原子的な条件付き引き落としが必要です。

**[上級] ラボでAP-LWWの後、誤差がちょうど668になったのはなぜですか?**

両側とも切断の開始時は1336でした。アジアの自分の書き込みがコピーを668まで動かし、純粋な変化は-668です。ヨーロッパが最後に書いたので、LWWはヨーロッパの760を残し、アジアの減少を捨てました。760 - 台帳の92 = 668多すぎます。

**[上級] CPの実行では、台帳と違う読み取りが0件でした。CPが線形化可能だと証明されますか?**

いいえ。チェッカーがテストするのは、記録された1つの履歴が、実時間を守る合法的な逐次順序を少なくとも1つ許すかどうかです。このシミュレーションの履歴(レプリケーションは瞬時、時計は完璧)はそれと矛盾しません。実装を証明するには、あり得るすべての履歴について考える必要があります。

**[上級] 長い分断の間、APの銀行は被害をどう抑えられますか?**

リスクに上限を付けます。分断中の引き出しに側ごとの許容量を設け、大きな金額は断り、すべての操作に一意のidを付け、回復時にログをマージし、ゼロを下回った口座を検知して補償します。

## チートシート
| 用語やルール | 意味 |
|---|---|
| CAP定理 | 分断中、データが変わるとき、線形化可能な読み取りと動いているすべてのノードからの答えの両方は保証できない |
| C(線形化可能性) | 1つのコピーのように振る舞い、操作の順序が実時間と一致する |
| A(CAPの可用性) | 故障していないノードへのすべてのリクエストがエラーでない応答を得る |
| P(分断耐性) | ノード間のメッセージが失われても動き続ける。選べるものではない |
| CP | 少数派の側は断る(読み取りも)。与えられた答えは最新 |
| AP | すべての側が自分のコピーから答える。読み取りは古いことがある。あとで修復 |
| クォーラム | 投票者の半分より多い数。片側だけが持てる |
| 証人 | データをほとんど持たない投票者で、同数を割る |
| ログのマージ | 両側の操作の和集合をidで、順序通りに再生する。何も失わない |
| Last-writer-wins | タイムスタンプが最新のものが勝ち、もう一方の書き込みは黙って捨てられる |
| 不変条件 | 「残高が0以上」のようなアプリケーションのルール。原子的なチェックが必要で、Cだけでは足りない |
| PACELC | 分断していればAかC。そうでなければレイテンシか整合性 |
