本記事は System Design Simple の英語記事の日本語版です。原文: https://systemdesignsimple.com/login-anomaly-detection-3am-rule/

午前1時から5時の固定ルールでログインの異常を検知すると、すべてのアカウントを同じ時計で判断することになります。夜がふだんの生活の人にまでアラームが鳴ります。1件のログインを、そのアカウント自身の過去と比べる方法に変えたら、私たちの合成データのラボでは誤報が1,000件あたり78.9件から3.8件に減り、仕込んだ不正ログインも多く捕まりました。


## ラボでの固定ルール
![24時間の時計ダイヤル。真夜中が上にあり、午前1時から5時の部分が赤く、1,000件あたり誤報78.9件という数字が下にある](https://systemdesignsimple.com/img/login-anomaly-detection-3am-rule/b01.webp)
*固定ルールは、時計の赤い1区切りをすべてのアカウントに当てはめるだけです。*

私たちのラボ([`labs/sd-60/run.mjs`](https://github.com/systemdesignsimple/labs/blob/main/labs/sd-60/run.mjs))は、200人の合成ユーザーについて30日分のログインを、固定のシードで作ります。ユーザーごとに自国と、ふだんログインする時間帯と、端末が1台か2台あります。ふつうの生活も混ぜてあります。約10%が夜勤で、約25%が月の中に海外へ出かけ、約15%が月の中に新しい電話を買い、正直なログインの3%がランダムな時刻に起きます。1日から7日目は履歴作りだけに使います。8日から30日目にかけて8,457件のログインを採点し、その中に不正を20件仕込みました。12件が「うるさい」もの(午前3時ごろ、新しい国、新しい端末)、3件が「海外の日中」(新しい国と端末、ただしその人のふだんの時刻)、3件が「静かな」もの(新しいのは端末だけ)、2件が「なりすまし」(自国、ふだんの時刻、すでに知っている端末ID)です。

時刻は、アカウントの自国の時間帯で測ります。固定ルールは、1時00分から4時59分のログインにアラートを出します。

| 検知方法 | 捕まえた不正ログイン | 誤報 | 1,000件あたり | 本物だったアラート |
|---|---|---|---|---|
| 固定の午前1時から5時ルール | 20件中13件 | 667件 | 78.9件 | 680件中13件(1.9%) |
| ユーザーごとの基準、アラートは4点 | 20件中15件 | 32件 | 3.8件 | 47件中15件(31.9%) |
| ユーザーごとの基準、アラートは2点 | 20件中19件 | 985件 | 116.5件 | 1.9% |

固定ルールは、うるさい攻撃12件をすべて捕まえました。あと1件、午前1時41分に起きたなりすましも、たまたま時間帯に入っていたので捕まえました。海外の日中と静かなログインは1件も捕まりませんでした。どれもその人のふだんの時刻に来たからです。

## ほとんどのアラートが間違っていた理由
適合率(アラートのうち本物だった割合)が1.9%まで下がった理由は、2つあります。

1つ目は、そもそもの発生率です。採点した8,457件のうち、不正は20件だけ。約0.24%です。探すものがそれだけ珍しいと、正直な99.76%の側で起きる小さな誤検知でも、本物の数を上回ってしまいます。適合率は「捕まえた件数 ÷ (捕まえた件数 + 誤報)」なので、13 ÷ (13 + 667) = 1.9%です。

2つ目は、ルールの切り取った時間帯に、正直な人がぎっしりいたことです。667件の誤報のうち442件(66.3%)が夜勤のユーザーから来ました。彼らにとって、その時間帯は勤務時間の真ん中です。

![667個の点。1つが固定ルールの誤報1件で、左側の442個が青く、66.3%が夜勤ユーザーと書かれている](https://systemdesignsimple.com/img/login-anomaly-detection-3am-rule/b04.webp)
*点1つが、固定ルールの誤報1件です。青い点は夜勤のユーザーから来ました。*

誤報が頻繁だと、本物の事件が見えにくくなります。[OWASPのロギングのチートシート](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#which-events-to-log)も、どのイベントを記録するかという話の中で、この危険に触れています。ここでは、本物のアラート13件が680件の待ち行列の中に埋もれました。[NIST SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final)は、ログの管理計画をどう立てるか、人がログを見直す作業も含めて扱っています。

## ユーザーごとの基準はログインにどう点をつけるか
基準は、アカウントごとに記録を残します。動画では「習慣カード」と呼んでいます。過去のログイン時刻、見たことのある国とその回数、見たことのある端末、前回のログインの国と時刻です。新しいログインは、その記録とだけ比べられます。

```text
# score per login (labs/sd-60/run.mjs, weights set by hand)
unusual hour         +2   under 5% of past logins within 1 hour of this time
                           (circular distance, so 23:30 and 00:15 are 45 min apart;
                            only scored after 5 past logins)
new country          +3   country never seen for this account
new device           +2   device never seen for this account
rapid country change +3   country differs from the previous login's, it is not
                           the account's usual country, and under 8 hours passed
alert when score >= 4
```

ふだんの国とは、過去のログインが最も多い国です。このルールは国の変化だけを見て、移動の速さを計算しません。だから、国境の近くやVPNの出口でも反応することがあります。

ラボの実際の2行で、計算を見てみましょう。17時09分、自国から、新しい端末での静かな攻撃は2点(新しい端末だけ)で、何も鳴りませんでした。04時15分、新しい国から、新しい端末でのうるさい攻撃は5点で、アラートが鳴りました。時刻では引っかかりませんでした。そのユーザーの履歴には、午前4時ごろのログインがすでにあったからです。

![点数のメーター。4のところに赤い線があり、ベルがある。新しい電話+2と新しい国+3のチップで、赤い部分が5まで伸びて線を越えている](https://systemdesignsimple.com/img/login-anomaly-detection-3am-rule/b06.webp)
*シグナルは足し算されます。私たちの設定では、4点でベルが鳴ります。*

ログインは、悪いものも含めてすべて履歴に入ります。届いた時点では区別がつかないからです。このラボは履歴をすべて残し、ログインのたびに過去の時刻を全部なめるので、採点は過去のログイン n 件に対して O(n) の時間です。本番の設計では、残す期間に上限を決め、更新のルールも決めておく必要があります。

基準の誤報32件は、29件が旅行者(ほとんどは海外での最初のログイン)で、3件が新しい電話でした。夜勤のユーザーが絡んだのは5件だけです。固定ルールの442件と比べれば、ずいぶん違います。MITREは、盗んだ認証情報でのログインを[T1078 Valid Accounts](https://attack.mitre.org/techniques/T1078/)に分類しています。

## しきい値はダイヤル
アラートのラインを4点から2点に下げたら、再現率(仕込んだ不正のうち捕まえた割合)は75%から95%に上がり、適合率は31.9%から1.9%に落ちました。下のラインは不正20件のうち19件を捕まえました。静かな3件となりすまし1件も含みます。代わりに、新しい端末だけのログインや、ふだんと違う時刻だけのログインにも、すべてフラグが立ちました。誤報985件、1,000件あたり116.5件。固定ルールの78.9件を上回ります。

これが、よくある適合率と再現率のトレードオフです(定義は[Wikipedia](https://en.wikipedia.org/wiki/Precision_and_recall)にあります)。アカウント乗っ取りを見逃すコストと、1件のアラートに使える担当者の時間から選んでください。変えるたびに、両方を測り直すことです。

## この設定が見逃したもの
仕込んだログインのうち4件は、固定ルールも、4点の基準もすり抜けました。静かな3件となりすまし1件です。自国から、ふだんの時刻に、新しい端末だけでログインすると、2点しかつきません。なりすまし2件は、アカウントがすでに持っていた端末IDを使っていました。1件は18時48分に2点、もう1件は01時41分に0点でした。

新しい端末での多要素認証を求めれば、盗んだパスワードでのログインには強くなります([OWASP認証チートシート](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#reauthentication-after-risk-events))。すでにサインイン済みのセッションの再利用は、ログインのイベント自体を出さないことがあります。私たちのラボは、どちらの場合も試していません。セッションの再利用には、セッションの側の対策が必要です。セッションの活動を監視し、セッションの寿命を短くし、メールアドレスの変更やAPIトークンの作成のような重要な操作の前には再認証を求めることです。[OWASPセッション管理チートシート](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#binding-the-session-id-to-other-user-properties)は、セッションを端末の性質に結びつける方法の限界を説明しています。そもそも、乗っ取られた端末はそのチェックをすり抜けます。私たちの[PHPセキュリティチェックリスト](https://systemdesignsimple.com/php-security-common-vulnerabilities/)には、セッションの基本がコードで載っています。

汚染も、もう1つの穴です。このラボでは、1回のログインでその国と端末が「見たことある」ものになります。最も多い国を変えるには繰り返し使う必要があり、それが変わると、その国に対する急な国の変化のシグナルも消えます。

## ラボを実行する
```sh
cd labs/sd-60
node run.mjs          # prints the table above and writes three CSV files
node chart-data.mjs   # same run, plus per-hour counts used for the video's charts
```

Node.js 22が必要で、パッケージもネットワークもいりません。1秒もかからず終わります。CSVには、アラートがすべて点数と理由つきで載り、仕込んだログインも、検知器が捕まえたかどうかつきで載ります。

## 私たちが実行したときに見たもの
2026年11月6日に、Macの[labs/sd-60](https://github.com/systemdesignsimple/labs/tree/main/labs/sd-60)の中で`node run.mjs`を実行しました。検知器ごとに1行ずつ出て、次に両方をすり抜けた不正ログインのまとめ、保存したCSVファイル、最後にRESULTのまとめが出ました。

![私たちのsd-60ラボ実行のターミナル出力: node run.mjs](https://systemdesignsimple.com/img/posts/login-anomaly-detection-3am-rule/lab-run.webp)
*私たちのラボ実行。検知器ごとの捕獲、見逃し、誤報が8,457件のログインについて出ています。*

午前1時から5時の固定ルールは、仕込んだ不正20件のうち13件を捕まえ、誤報667件、1,000件あたり78.9件でした。4点のユーザーごとの基準は15件を捕まえ、誤報32件、1,000件あたり3.8件でした(どちらの率も小数第1位に丸めています)。驚いたのは夜勤の数です。固定ルールの誤報のうち442件が夜勤のユーザーに落ちたのに対し、基準では5件でした。アラートの大半は、合成データで「悪くない」としたログインに飛んでいました。

この合成データの実行では、時間帯のルールは、夜働くように設定したユーザーを主に引っかけました。ログインを1件ずつ、そのアカウント自身の習慣と比べる方法は、誤報をはるかに少なくしました。それでも、不正4件は両方の検知器をすり抜けました。

## 私たちの見解
固定の時間帯は、書くのも説明するのも簡単です。うるさい攻撃は全部捕まえました。代償は誤報の洪水でした。正しい13件に対して、間違った667件。その大半は、ふだんの仕事をしている人へのものでした。ログインを1件ずつ、そのアカウント自身の習慣と比べる方法は、うるさい攻撃の捕獲を保ったまま、海外の日中の3件も加え、私たちのデータでは誤報を約20分の1に減らしました。4点の基準は、なりすまし2件を両方見逃しました。固定ルールは、そのうち1件を時間帯に入っていたので捕まえました。行動の採点は、MFAやセッションの対策と並べる1つの層として扱ってください。[信頼できない文章を読むAIエージェント](https://systemdesignsimple.com/why-the-ai-obeyed-a-hidden-line/)でも、同じ重ね方をしています。私たちの数字は、攻撃の組み合わせと重みを自分たちで選んだ合成データからのものです。トレードオフの形を示すもので、本番で見る率ではありません。私たちの[偽のパスワード漏えいテスト](https://systemdesignsimple.com/did-the-ai-leak-my-fake-password/)も、合成の入力を使っています。

この記事は、一般的な監視のパターンと公開のドキュメント、私たち自身の合成データのラボを説明したものです。特定の企業の非公開のシステムを説明したものではありません。図は概念図です。すべての数字は[labs/sd-60](https://github.com/systemdesignsimple/labs/tree/main/labs/sd-60)(シード60、合成ユーザー200人、30日間、自分たちで選んだ攻撃の組み合わせと手で決めた重み)から来ています。Apple M2 Pro 1台、Node v22.13.1で実行しました。攻撃の手法は示していません。
