SQLかNoSQLかを考えるとき、まず見るべきはアクセスパターンです。アクセスパターンがデータの形を決め、形がコストのほとんどを決めます。そして多くのデータベースは、どちらの形も持てます。私たちのラボでは、1つのSQLiteエンジンに同じ10万人のユーザーを正規化テーブルと1ユーザー1ドキュメントの2つの形で入れました。勝者はワークロードによって入れ替わりました。


## アクセスパターンから、どう SQL か NoSQL かを考えるか
「SQLかNoSQLか」は2つの決定をごちゃ混ぜにしています。1つはデータの形です。共有する事実を自分のレコードに置いてIDでつなぐか、関連するデータを1つの自己完結したレコードの中に入れるか。もう1つはデータベース製品です。この2つは必ずしも一緒に動きません。SQLiteとPostgreSQLはカラムにJSONドキュメントを格納できます([SQLiteのJSON関数](https://www.sqlite.org/json1.html)、[PostgreSQLのJSON型](https://www.postgresql.org/docs/current/datatype-json.html))。MongoDB自身のモデリングガイドも、埋め込みではなく参照を使うべき場合を説明しています([埋め込みと参照](https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/))。

**正規化**とは、キーと依存関係を軸に関係を整理し、重複と更新の不整合を減らすことです。ここでは商品名は `products` に置き、注文明細は商品IDで商品を指します。
**埋め込み**とは、関連するデータを親のレコードの中に格納することです。このラボでは共有される商品名を注文明細へコピーして非正規化もしているため、各ユーザードキュメントは注文を名前付きで持っています。

だから、まずアプリが何をいちばんするかを見てください。1つのオブジェクト全体を読むのか、それとも多くのオブジェクトが共有するデータを変えるのか。答えが出たら形を選び、その形をうまく扱えるデータベースを選びます。同じ考え方は、[読み取りと書き込みをデータベースで分ける](https://systemdesignsimple.com/one-database-writes-ten-read/)ときにも出てきます。ワークロードが先です。

## 私たちのラボが測ったこと
このラボ(`labs/sd-21/run.mjs`)は、Node 22内蔵の `node:sqlite` を使って1つのインメモリSQLiteデータベースを作り、同じ合成ショップデータを2つの形で読み込みます。エンジンもプロセスもメモリも共有しているので、ベンダー、ネットワーク、ドライバの違いは外れていて、変わるのは形だけです。

```text
-- shapes
normalized: users(id, name, email)
            products(id, name, price_cents)
            orders(id, user_id, product_id, qty, price_cents, ordered_at)  + index on orders(user_id)
document:   user_docs(user_id, doc)   doc = {"id":8, ..., "orders":[{"productName":"Product 0001", ...}, ...]}

-- data (seed 21)
100,000 users · 1 to 9 order lines each (500,397 total) · 1,000 products
popularity 1/rank: product 1 is in 13.5% of order lines and in 47,999 user documents
```

計測するペアはどちらも両方の形で実行し、先に実行する形を交互に入れ替えます。結果はすべて検証します。両方の形が同じプロフィールと同じレポート行を返さなければならず、名前変更の後に古いコピーが残ってはいけません。10万人ユーザー、1台のApple M2 Proでの結果です。

| ワークロード | テーブル (中央値) | ドキュメント (中央値) | サンプル数 | 勝者 |
|---|---|---|---|---|
| 注文付きプロフィールを1件読み込む | 0.0130 ms | 0.0036 ms | 各300 | ドキュメント、3.6倍 |
| いちばん人気の商品名を変更する | 0.017 ms、1行 | 628 ms、47,999件書き換え | 各5 | テーブル、数千倍 |
| 全ユーザーの商品別売上 | 249.5 ms | 982.4 ms | 各2 | 結論なし(サンプル不足) |

名前変更の比率は大きいですが、正確さには限りがあります。0.017 msはラボのタイマーの下限の約2倍にすぎないため、「数千倍」がこのラボで言えるいちばん正確な表現です。

## なぜ1つの名前変更が47,999件のドキュメントを書き換えたのか
テーブルでは、名前変更は `UPDATE products SET name = ? WHERE id = 1` です。1行、28論理バイトです。ドキュメントでは、その名前のコピーすべてを変えなければならず、ラボにはJSON配列の中にネストした値へのインデックスがないため、すべてのドキュメントの中を探します。

```sql
-- sd-21 rename, document shape (one transaction)
SELECT user_id, doc FROM user_docs d
WHERE EXISTS (SELECT 1 FROM json_each(d.doc, '$.orders') j
              WHERE json_extract(j.value, '$.productId') = ?);
-- then, for each match: parse, change the name, UPDATE user_docs SET doc = ? WHERE user_id = ?
```

10万件のドキュメントをスキャンしました。アプリケーションは47,999件のドキュメントを再シリアライズし、論理的なJSONコンテンツにして合計34.4 MBを書き込みました。ラボはディスクページ、WAL、fsyncのトラフィックを測っていないため、ディスク上のタイミングの差を予測することはできません。PostgreSQLはストレージのコストを1つ文書化しています。UPDATEは新しい行バージョンを書き、大きなjsonbドキュメントのような大きなフィールド値はTOASTストレージに置かれ、圧縮されるかチャンクに分割されるため、変わった値はもう一度格納されます([PostgreSQLのTOAST](https://www.postgresql.org/docs/18/storage-toast.html))。

MongoDBは配列フィールドに[マルチキーインデックス](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-multikey/)を持っています。クエリプランナーがそのインデックスを選べば、すべてのドキュメントをスキャンしなくても該当するドキュメントを見つけられます。ただし、現在の名前を維持するには、該当するすべてのドキュメントを更新しなければなりません。部分更新の演算子はドキュメントごとに送るバイト数を減らしますが、更新するドキュメントの数は変わりません。コストは、コピーを持つレコードの数とともに増えます。だからこそ、ラボはいちばん人気の商品の名前をあえて変えたのです。

ラボは各名前変更を直列に実行し、その後で古いコピーが残っていないか確認します。同時実行のトラフィックはテストしていません。同時書き込みのもとでは、コピーの経路にもう1つのリスクがあります。古い読み取りから作ったドキュメントで置き換えると、分離やバージョンチェックがなければ、同時に行われた変更を上書きしてしまうことがあります。アトミックなフィールド更新か、リトライ付きのcompare-and-swapを使ってください。コピーをドキュメント間でアトミックに変えなければならない場合は、データベースのトランザクション保証を確認してください。同時更新については、[共有の席をトランザクションがどう守るか](https://systemdesignsimple.com/two-fans-one-seat/)も見てください。遅れて届くかもしれないコピーについては、[結果整合性が何を許すか](https://systemdesignsimple.com/like-count-wrong-balance-never/)をご覧ください。

## なぜドキュメントがプロフィール読み取りで勝ったのか
注文付きのプロフィールを読み込むとき、ドキュメントの形は主キー検索1回と `JSON.parse` 1回です。正規化された形は、2つの結合を持つクエリを1回実行します(ユーザーを `orders(user_id)` インデックス経由で注文へ、次に各注文を主キーで商品へつなぎます)。そしてネストしたオブジェクトをJavaScriptで組み立て直します。ラボの見積もりでは、正規化されたプロフィールは論理レコードにして約11件、ドキュメントは1件です。物理的なページ読み取りは測っていません。どちらの経路もプロフィールごとにクエリは1回です。測った差には、SQLiteの実行、結果の変換、JavaScriptのオブジェクト構築が含まれています。本番のレイテンシには、別にベンチマークが必要です。

売上レポートは逆の側面を示しています。ドキュメントの形は、作られていない問いかけに答えるために `json_each` ですべてのドキュメントを解析しなければなりません。10万人ユーザーでは、形ごとに2サンプルしか取れず、ラボの3サンプルというルールを下回ったため、勝者は出しません。1万人ユーザーでは27サンプルが取れ、テーブルが5.3倍速いという結果でした(19.7 ms対104.8 ms)。

## 形の選び方
1. いちばん多い読み取りと書き込みを、おおよその頻度とともに挙げます。「プロフィール読み込み、2,000件/秒」「商品名の変更、1日数件」「レポート、1時間ごと」といった具合です。
2. 一緒に読まれ、親が所有し、サイズに上限があるものは埋め込みます。ユーザーの設定や、投稿の直近数件のコメントなどです。
3. 共有され、変わるものは参照します。商品名と価格、ユーザーの表示名などです。古いコピーが許せる場合か、意図的にスナップショットを残す場合にだけコピーしてください(注文は支払ったときの価格を保持すべきです)。
4. 成長に気をつけてください。1つのドキュメントの中の無制限の配列は、読み取りも書き換えもすべて遅くします。
5. そのうえで、インデックス、トランザクション、スケーリングのモデルがその形と頻度に合うデータベースを選びます。これは、[上に伸ばすか横に伸ばすか](https://systemdesignsimple.com/vertical-vs-horizontal-scaling/)を決めるときと同じ「要件が先」という習慣です。

## トレードオフ
| 形 | 向いている用途 | 払うコスト | 使うべきとき |
|---|---|---|---|
| 正規化テーブル | 共有する事実の変更、全データにまたがるアドホックな問い合わせ、強い制約 | オブジェクト全体を読むたびに結合が必要 | 共有データが変わる、または問い合わせを予測できない |
| 埋め込みドキュメント | 1つのオブジェクト全体を1回の検索で読む | 同期を保つコピー、書き込み増幅、横断的な問い合わせのスキャン | データが一緒に読まれ、1つの親が所有し、共有がまれ |
| ハイブリッド(ドキュメント内のID、またはテーブル内のJSONカラム) | ほとんどの実際のアプリ | 2つのモデルを整合させる手間 | 頻繁な読み取りに1つのオブジェクトが必要で、共有する事実は1か所に残す |

## 私たちの見解
プロフィールの読み込みではドキュメントが速く、共有する商品の名前変更では正規化テーブルが速かった。アプリがいちばん多く行う2つか3つの操作から出発し、その操作を安くする形を選んでください。SQLかNoSQLかという製品の選択は、その次の決定です。共有され、変わるデータは1か所に置き、所有され、一緒に読まれるものだけを埋め込んでください。その操作をまだ挙げられないなら、私たちはテーブルから始めます。共有する変更と新しい問い合わせを安く保てるからです。

これらのタイミングは、1台のマシンでの合成されたインメモリのワークロードに当てはまるものです。このラボはデータベース製品を比較していません。製品の動作は公開されているドキュメントから説明しています。
