本記事は System Design Simple の英語記事の日本語版です。原文: https://systemdesignsimple.com/how-search-skips-96-percent-of-vectors/

HNSWベクトル検索は、「このクエリにいちばん近いベクトルはどれか」に、クエリとすべてのベクトルを比べることなく答えます。近いベクトル同士を結んだ層状のグラフを歩き、結果リストが埋まって、まだ調べていない候補のうちいちばん近いものが、保持している最悪の結果より遠くなったら止めます。代償として、答えは近似です。私たちのラボでは20,000本の合成ベクトルで、このダイヤルがrecallを0.750から0.944へ動かし、クエリあたりの仕事は145本から776本へ増えました。面接用の言い方: 「ユーザーが写真ライブラリに『ビーチの犬』と打ちます。すべての写真を読まずに検索できる設計にしてください。」


## まず知っておくこと
### 埋め込み

埋め込みモデルは、コンテンツを決まった長さの数のリストに変え、関連するコンテンツが近いベクトルになるようにします。言葉や文でそれがどう働くか、車の検索がvehicleを見つける理由は、[埋め込みの解説(AI 11)](https://systemdesignsimple.com/why-search-for-car-finds-vehicle/)にあります。この記事はそこから先です。ベクトルはもう手元にあって、近いものを速く見つける方法が問いです。

### 写真と文字のための1つの空間

打った文で写真を探すには、写真のベクトルと文のベクトルが比べられなければなりません。CLIP(Radfordら、2021)は、画像用とテキスト用の2つのエンコーダーを、4億組の画像とテキストのペアで一緒に学習させます。合う写真とキャプションはコサイン類似度が高くなるよう引き寄せられ、同じバッチの合わないペアは引き離されます。学習のあと、「ビーチの犬」というテキストは、ビーチの犬の写真の近くに来ます。私たちのラボでは、どんなモデルも動かしていません。合成ベクトルを作り、検索のコストとrecallだけを測りました。

![画像側とテキスト側を一緒に学習させたモデルの図。犬の写真と「ビーチの犬」という言葉が、どちらも数の列になって地図上の同じ場所に来る](https://systemdesignsimple.com/img/how-search-skips-96-percent-of-vectors/b03.webp)

### 距離とコサイン

ラボでは二乗ユークリッド距離‖q - x‖²で順位を付けます。長さが1のベクトル(CLIP式のモデルは正規化したベクトルを比べます)では、‖q - x‖² = 2 - 2·cos(q, x)なので、二乗距離が小さい順は、コサインが大きい順とまったく同じになります。Faissやhnswlibのようなライブラリは両方の指標を用意しています。正規化したベクトルでは、順位ではなく数値だけが変わります。

## 用語の定義
**k近傍探索(kNN)**: クエリベクトルに対して、距離がいちばん小さいk本の保存ベクトルを返すことです。ラボではk = 10です。
**フルスキャン(フラットインデックス)**: クエリと保存されたすべてのベクトルの距離を計算し、いちばん良いk本を残します。作りから厳密ですが、コストはN × dで増えます。
**近似最近傍(ANN)インデックス**: フルスキャンよりずっと少ない距離計算で、本当のk近傍のほとんどを返す構造です。
**HNSW**: 階層的航行可能スモールワールドグラフです。すべてのベクトルが層0のノードで、近いノードとリンクします。ランダムに、幾何級数的に減る一部が上の層にも現れ、長い距離をまたぐリンクを持ちます。
**M、M0、efConstruction**: 構築時のパラメーターです。Mは新しいノードが層ごとに得るリンクの数(上の層の上限でもあります)、M0は層0の上限、efConstructionはそのリンクを探す検索の広さです。ラボでは12、24、60を使いました。
**efSearch**: クエリ時の広さで、最下層の探索が探索中に保持する候補の数です。k以上でなければなりません。
**Recall@10**: フルスキャンによる本当の近傍10本のうち、インデックスが何本返したかを、クエリで平均したものです。200回のクエリでは、2,000本のうちのヒット数です。
**距離計算と触れた異なるベクトル**: ラボでは両方を数えます。計算は、距離を計算するたびに数えます。2つの層で到達したベクトルは2回数えます。異なるベクトルは、クエリごとにIDを1回だけ数え、「3.9%」はこの数え方です。

## HNSWはどうやってほとんどのベクトルをスキップするのか
ラボ([`labs/ai-12/run.mjs`](https://github.com/systemdesignsimple/labs/blob/main/labs/ai-12/run.mjs))は、64個の数からなるベクトル20,000本を100クラスタで作ります。各クラスタは、実際には8つの隠れた方向にだけばらつき、あとは少しのノイズです。本物の埋め込みが一様なノイズではなく塊になるのと同じです。同じ分布からクエリベクトルを200本引き(ほかに時間計測なしのウォームアップ20本)、フルスキャンでそれぞれの厳密なトップ10を計算し、素のJavaScriptでHNSWインデックスを構築して、6つのefSearch設定で検索します。シードは固定なので、データ、グラフ、すべての回数とrecallの値は、実行ごとにまったく同じになります。

![保存されたベクトルを家の点で描いた地図。光る点の列がクエリのピンへ向かい、「写真検索、4%未満をチェック」と書かれた電話がある](https://systemdesignsimple.com/img/how-search-skips-96-percent-of-vectors/b01.webp)

フルスキャンが基準です。クエリあたり20,000回、64次元の距離計算、つまり1,280,000回の座標の寄与で、引き算と二乗と加算が毎回要り、recallは1.000です。

### 層: 何本のノードが上へ行くか

ベクトルを挿入するとき、指数関数的に減る分布からトップの層を引きます。論文のルールで、ラボもこれに従います。

```text
level = floor( -ln(U) · mL ),   U は (0, 1] の一様乱数,   mL = 1 / ln(M)

P(level >= l) = M^(-l)                         ラボ: M = 12, mL = 1 / ln 12 = 0.402

level l 以上に達するノード、20,000本     期待値 20,000 / 12^l     ラボのグラフ
level >= 1                                 1,667                      1,681
level >= 2                                 139                        140
level >= 3                                 11.6                       6
いちばん上の層                             約 ln(20,000) / ln(12) = 9.90 / 2.48 = 3.99    3
```

つまり18,319本のベクトルは層0にだけいて、6本が層3にいます。各層は下の層の約12分の1のまばらさで、それが上の層を役立てます。ノードが少ないので、2つのノードのリンクはたいてい長い距離をまたぎます。

![短い糸が家どうしを近くで結び、その上に半透明の上の層があって、少数の家が長い糸で結ばれている](https://systemdesignsimple.com/img/how-search-skips-96-percent-of-vectors/b04.webp)

### 挿入: リンクの選び方

レベルLのベクトルvを挿入するには、ビルダーは最上層の全体の入口から始めて、層L + 1まで貪欲に(いちばん良い候補だけを残して)歩きます。層Lから0までは、efConstruction = 60の候補を残す広い検索を走らせ、そこからM = 12本をリンクとして選びます。ラボでは論文のヒューリスティックを使います。候補を近い順に見て、すでに残した隣接ノードのどれよりもvに近いものだけを残し、あとでスキップした中でいちばん近いものを足して埋めます。このルールはリンクをいろいろな方向へ広げます。論文によれば、クラスタ化したデータでいちばん効きます。近い順だけのリンクでは、クラスタの結びつきが弱くなるからです。選んだ隣接ノードはどれもvへの逆リンクを得ます。リストが上限(上は12、層0はM0 = 24)を超えたら、ラボではいちばん近いものだけに切り詰めます。これは一部のライブラリより単純な手順です。

### 検索: 遠くへ跳んで、近くを歩く

クエリは同じ2つの段階で動きます。

```text
ep = 入口(いちばん上の層にあるノード)
for layer = 最上層 から 1 まで:
    ep = この層で ep からサイズ1のリストで貪欲に探索する      # 遠くへ跳ぶ
results = 層0で ep からサイズ max(efSearch, k) のリストでビーム探索する   # 近くを歩く
いちばん良い k 本を返す

ビーム探索は2つのヒープと訪問済み集合を保持します。
    candidates   まだ広げるノード、近い順
    results      これまでに見た中でいちばん良い ef 本、最悪が上
開始: (dist(q, ep), ep) を candidates と results に入れ、ep を訪問済みにする
candidates が空でない間くり返す: いちばん近い候補 c を取り出す
    results.size == ef かつ dist(c) > 最悪の結果の距離なら止める
    c の隣接ノード n ごとに:
        n が訪問済みなら次へ
        n を訪問済みにする
        dn = dist(q, n)
        results.size < ef または dn < 最悪の結果の距離なら:
            (dn, n) を candidates と results に入れる
            results.size > ef なら最悪の結果を除く
```

検索は、結果のヒープが埋まって、キューにあるいちばん近い候補が保持している最悪の結果より遠いとき、またはキューが空になったときに止まります。このルールは、調べていない側とすでに持っているものを比べるだけで、本当の近傍が結果に入っているかは確かめません。efが大きいほど、越えなければならないリストが長くなり、歩く距離も長くなります。[hnswlibの`searchBaseLayerST`](https://github.com/nmslib/hnswlib/blob/master/hnswlib/hnswalg.h)も同じ条件を実装しています。論文では、層の構造により、分析するデータではホップ数がおよそlog Nで増えると主張しています。ここから対数スケールの主張が来ます。ラボはN = 20,000でしか実行していないので、このスケールはテストしていません。

## 25分の1の仕事なのに7倍しか速くない理由
代表の実行は7回のうち5回目です(`output.txt`、`results.json`)。

```text
フルスキャン          平均2.175ミリ秒   p95 2.243ミリ秒   20,000回の評価   recall 1.000
HNSW、efSearch 320    平均0.296ミリ秒   p95 0.450ミリ秒      794回の評価   異なるベクトル776   recall 0.944

仕事の比     20,000 / 794   = 25.2倍少ない評価
時間の比     2.175 / 0.296  = 7.35倍   (ラボは丸めていない平均から7.36と出しています)

距離計算1回あたりのクエリ時間
  フルスキャン    2.175ミリ秒 / 20,000 = 0.109マイクロ秒
  HNSW         0.296ミリ秒 / 794    = 0.373マイクロ秒   (1回あたり3.4倍)
```

![「触れた異なるベクトル 平均776本、3.9%」と速度を書いたラボのターミナルカードと、インデックスのバーが先に止まる2本のバーのレース](https://systemdesignsimple.com/img/how-search-skips-96-percent-of-vectors/b06.webp)

スキャンは1本のFloat32Arrayを先頭から最後まで読みます。クエリあたり5.12 MBで、JavaScriptのJITがきつくコンパイルするループで、アクセスは順番です。0.373マイクロ秒は、HNSWのクエリ時間の合計を評価回数で割ったものなので、距離の計算以外の歩行のすべてを含みます。グラフの歩行では、不規則なメモリアクセス、ヒープ操作、訪問チェックが入ります。これらが1回あたりのコストを上げることはありえますが、このラボでは寄与を分けても、キャッシュミスを測ってもいません。保持する結果のヒープは最大でef件で、操作はO(log ef)です。候補のヒープはefを超えて大きくなることもあり、操作はO(log C)で、Cはその時点の大きさです。SIMDの距離計算を持つC++ライブラリでは両方が速くなります。そのとき比がどう動くかは、ここではテストしていません。

## efSearchのダイヤル: recallと速度の交換
代表の実行からの掃引です。

| フルスキャン | 20,000 | 20,000 | 100% | 2.175 | 2.243 | 1.000 |

![efSearchと書かれたダイヤルを320から10へ回すと、recallのバーが約94%から75%へ下がり、「95%の目標には届かなかった」と書かれている](https://systemdesignsimple.com/img/how-search-skips-96-percent-of-vectors/b07.webp)

efSearch 10のrecallは、ちょうど2,000本のうち1,500本です。320では2,000本のうち1,887本なので、200回のクエリで113本の本当の近傍をまだ見逃しています。10から160まで、倍にするたびにrecallはおよそ3から4ポイント上がり、触れるベクトルは36から54本増えました。最後の倍、160から320では、5.4ポイントのために445本増え、仕事は2倍以上になりました。20,000本に100クラスタあるので、クラスタの平均は200本です。上のトレースが仕組みを示しました。efがクエリのクラスタの大きさを超えると、結果リストは隣のクラスタからしか埋められません。平均もそのこぼれと一致します。

ラボのルールは「recall 0.95に届くいちばん小さいefSearchを選ぶ。なければ、いちばん良いものを報告する」でした。どれも届かなかったので、選んだ設定は320で、`results.json`には「選んだ設定は目標のrecallに到達: 0」と記録されています。320より上の設定や、MやefConstructionのほかの値はテストしていません。論文とライブラリのドキュメントでは、MやefConstructionを上げれば、より高いrecallに届くグラフが作れると説明しています。構築時間とメモリを払います。ここで0.95に届いたかどうかは不明です。

efSearchは、よくあるライブラリではクエリ時の設定です(hnswlibの`set_ef`、FaissのHNSWインデックスの`efSearch`フィールド、pgvectorの`hnsw.ef_search`で既定値は40)。再構築なしに調整できます。インデックスは自分の見逃しを報告できません。recallは、ラボのように厳密なスキャンと比べたときだけ分かります。

## インデックスのコストとB-treeとの違い
```text
ベクトル      20,000 × 64 × 4バイト                     = 5,120,000 B = 5.12 MB (float32)
リンク        リンク1本を4バイトのIDとすると約1.61 MB(推定で、測ったヒープではありません)
             1.61 MB / 4 B = 約400,000本のリンク、ベクトルあたり約20本
             すべてが上限まで埋まった場合の上限: 層0は 20,000 × 24 × 4 B = 1.92 MB
                                         + 上の層1,827リスト × 12 × 4 B = 0.09 MB  -> 約2.01 MB
オーバーヘッド     1.61 / 5.12 = ベクトルの31%上乗せ

構築        2.49秒、挿入1本あたり510回の距離計算
             510 × 20,000 = 1,020万回の評価 = フルスキャン510回分の仕事
元を取るまで      仕事: 10,200,000 / (20,000 - 794) = 10,200,000 / 19,206 = 約531クエリ
             時間(実行5): 2,490ミリ秒 / (2.175 - 0.296)ミリ秒 = 2,490 / 1.879 = 約1,325クエリ
```

上の層のリスト1,827本は、トレースの層の数1,681 + 140 + 6から来ます。時間の元を取るまでの数値が仕事の数値と違うのは、高速化の比と同じ理由です。実際のJavaScriptのヒープ使用量は、これらのペイロードの数値より大きく、測っていません。

規模の目安として、512次元の写真が100万枚あると仮定すると、float32で1,000,000 × 512 × 4 = 2.048 GBのベクトルで、ラボのM0 = 24なら層0のリンクは最大で1,000,000 × 24 × 4 = 96 MBです。この計算は仮定であって、実行ではありません。インデックスはたいていRAMに置きます。グラフの歩行がディスクからランダムなページを取りに行くと、ホップごとにディスクのレイテンシを払います。

### B-treeと同じ考え方、違う保証

![「仕事は少ない、答えは同じ」と書かれた小さなB-treeのデータベースカードが、オレンジ色の矢印で「HNSW、仕事は少ない、数本見逃すことがある」と書かれた糸のネットワークとつながっている](https://systemdesignsimple.com/img/how-search-skips-96-percent-of-vectors/b08.webp)

メインシリーズの30回目、SQLのチューニングとインデックスは、[無料のSystem Designコース](https://systemdesignsimple.com/learn/)にあります。[PostgreSQLのB-treeインデックス](https://www.postgresql.org/docs/current/indexes-types.html)は、順序のある値に働きます。すべてのキーは、ほかのキーより小さいか、等しいか、大きいかのどれかです。ルートページから降りるとき、検索キーと区切りキーを比べて、部分木全体を確実に除外できるので、数ページを読むだけで、逐次スキャンとまったく同じ行が返ります。プランナーはどちらの経路も選べます。結果の集合は同じです。

B-treeの固定されたキーの順序は、ふつう、任意のクエリに対する距離の順には並びません。1つの固定されたクエリに対する距離なら順序が付けられますが、クエリごとに別の順序が必要で、保存したインデックスは1つしか持てません。空間木は距離の上限で枝刈りできますが、次元が上がるとその枝刈りは効かなくなることが多いので、ベクトル検索のシステムはグラフ(HNSW)、クラスタのリスト(IVF)、圧縮(積量子化)を使います。HNSWのリンクは、たいてい本当の近傍へ導きますが、ときどき導きません。pgvectorのREADMEは、利用者側からこう書いています。クエリは既定で厳密で、HNSWやIVFFlatのインデックスを足すと近似になるので、結果が変わることがあります。B-treeは同じ答えのためにより少ない仕事をします。HNSWはより少ない仕事をし、数本見逃すことがあります。

## 私たちの見解
HNSWは、読み取りの多い検索で、RAMに収まる場合の妥当な既定値です。仕事の量を先に置きましょう。クエリあたりの評価回数は、使うマシンに依存しません。速度は中央値と範囲で報告します。efSearchは、触れたベクトルの数に対するrecallの曲線で調整します。0.95の目標に届かなかったのは、失敗ではなく、測った結果です。320より上を試していないので、届くかどうかは分かりません。さらに深く知るには、層になったグラフ検索についての[HNSWの論文](https://arxiv.org/abs/1603.09320)をお読みください。

## 練習問題

**[初級] 20,000本のベクトルのうち、HNSWはefSearch 320で何本に触れ、何本をスキップしましたか?**

クエリあたり平均776本の異なるベクトル、3.88%なので、約96.1%は一度も比べませんでした。

**[中級] M = 12のとき、20,000本のノードのうち何本がレベル2に達するはずで、実際は何本でしたか?**

P(level ≥ 2) = 12^(-2)なので、20,000 / 144 = 139本が期待値です。ラボのグラフは140本でした。

**[中級] 層0のビーム探索はいつ止まりますか?**

結果リストがef件埋まって、まだ調べていない候補のうちいちばん近いものが、保持している最悪の結果より遠くなったとき、または候補のキューが空になったときです。efが大きいほど、越えなければならないリストが長くなり、歩く距離も長くなります。

**[上級] 794回に対して20,000回は25.2倍少ない仕事です。なぜ7.36倍しか速くないのですか?**

距離計算1回あたりのクエリ時間は、HNSWが約0.373マイクロ秒、スキャンが約0.109マイクロ秒でした。グラフの歩行では、不規則なメモリアクセス、ヒープ操作、訪問チェックが加わります。ラボではそれらの寄与を分けても、キャッシュミスを測ってもいません。

**[上級] efSearch 160から320へ上げると、5.4ポイントのrecallのために触れるベクトルが445本増えました。なぜ急に増えるのですか?**

クラスタの平均は200本です。結果リストがクエリのクラスタより大きくなると、隣のクラスタからしか埋められません。トレースが示しています。320では、クラスタ68の194本すべてに、ほかのクラスタから446本が加わりました。

## チートシート
| 用語や式 | 意味 |
|---|---|
| フルスキャンのコスト | クエリあたりN × d回の座標の寄与。ラボでは20,000 × 64 = 128万回 |
| ベクトルのメモリ | N × d × 4バイト。ラボでは5.12 MB |
| リンクのメモリ(推定) | 保存したリンク × 4バイト。ラボでは約1.61 MB |
| 層のルール | floor(-ln U · mL)、mL = 1/ln M。P(level ≥ l) = M^(-l) |
| M、M0 | 新しいノードあたりのリンクと層0の上限(ラボでは12と24) |
| efConstruction | 構築時の検索の広さ。ラボでは60 |
| efSearch | クエリ時の結果リストの大きさ、k以上。recallのダイヤル |
| 止まる条件 | 結果リストが埋まって、キューにあるいちばん近い候補が保持している最悪の結果より遠いとき、またはキューが空のとき |
| Recall@10 | 本当のトップ10のうち見つけた割合の平均。ef 10で0.750、ef 320で0.944 |
| 距離計算と触れた異なるベクトル | 計算した距離の回数と、クエリごとにIDを1回だけ数えた数(794回と776本) |
| 単位ベクトルの恒等式 | ‖q - x‖² = 2 - 2·cos(q, x) |
| B-treeとHNSW | スキャンと同じ答えと、数本見逃すことがある |

## さらに読む
- [MalkovとYashunin](https://arxiv.org/abs/1603.09320)は、HNSWの挿入と検索のアルゴリズム、層の分布、近傍を選ぶヒューリスティック、Mとefの由来を示しています。
- [Radfordら(CLIP)](https://arxiv.org/abs/2103.00020)は、画像エンコーダーとテキストエンコーダーを一緒に学習させて、1つの埋め込み空間に入れる方法を示しています。
- [Faissのインデックスのページ](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)には、厳密なフラットインデックスと並んでHNSW、IVF、積量子化があり、それぞれのパラメーターが載っています。
- [hnswlib](https://github.com/nmslib/hnswlib)は広く使われているHNSWの実装です。そのヘッダー`hnswalg.h`に、検索のループと削除済みマークのロジックがあります。
- [pgvector](https://github.com/pgvector/pgvector)は、PostgreSQLの中のHNSWとIVFFlat、厳密な結果と近似の結果、フィルタリング、反復スキャンを扱います。
- [ANN-Benchmarks](https://arxiv.org/abs/1807.05614)は、クエリ毎秒に対するrecallでANNライブラリを比べる方法を説明しています。

このシリーズの関連記事: これらのインデックスを使う検索のループは、[100ページから1行を見つけるAI(AI 4)](https://systemdesignsimple.com/how-ai-finds-one-line-in-100-pages/)にあり、負荷の下で検索の層の大きさを決める計算は、[性能とスケーラビリティ、計測](https://systemdesignsimple.com/fast-alone-slow-crowded/)にあります。
