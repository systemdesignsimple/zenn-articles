記録した座標は、ボタンが動くと外れます。画面を一度も見ないリプレイボットは、それでも「完了」と報告します。私たちがコンピュータ利用エージェントのループをシミュレーションしたところ、ボタンが1つ動いたあと、リプレイは50タスク中2回しか終えられませんでした。ラベルを見てから動くボットは43回(86%)、動作のたびに画面を確認するボットは47回(94%)終え、この50回で黙った失敗は0回でした。


## 前提知識
モデルがあなたのマウスに直接触れることはありません。モデルはツール経由で動作を頼み、アプリケーションがそれを実行します。[AIクライアントが新しいツールを学ぶ仕組み(AI 13)](https://systemdesignsimple.com/how-ai-learns-new-apps-tool-discovery/)と同じ分かれ方です。コンピュータ利用では、その動作が「スクリーンショットを撮る」「x, yでクリックする」「この文字を入力する」といったものになります。

アプリケーションは毎ターン、会話の文脈を渡します([エージェントが履歴を送り直す理由](https://systemdesignsimple.com/why-an-ai-agent-re-sends-its-history/))。その文脈を削ったり圧縮したりすることもあります([長い会話で名前を忘れる理由](https://systemdesignsimple.com/my-chat-forgot-my-name/))。スクリーンショットが1枚増えるたびに、時間と文脈が増えます。それが、後で出てくる確認の代償です。

## 用語の定義
**リプレイ自動化**: 記録した動作を繰り返すスクリプト。ここでは各クリックの正確な画面位置を、画面をもう一度見ることなく繰り返します。
**観測**: エージェントが動作の前に画面から読み取るもの。見えるラベルとその位置などです。実際のエージェントはスクリーンショットと視覚モデルから得ます。私たちのラボはページの状態から読み取り、エラーを加えます。
**黙った失敗**: ボットがタスクを完了したと報告するのに、ページが求められた結果を保存していないことです。
**制限付き再試行**: 失敗したステップを決まった回数(ここでは1回)だけ繰り返すこと。再試行の前にまず見るのは、そのステップがすでに終わっているかもしれないからです。回数を使い切ったら、ループせずに失敗を報告します。

## コンピュータ利用エージェントはどうやって正しいボタンを押すのか
スクリーンショットを使うエージェントは、ツール経由で観測を頼み、次の動作を決め、アプリケーションに実行を頼みます。アプリケーションは動作を実行し、観測を返します。スクリーンショットを自動で付けることも、エージェントが頼むこともあります。Claudeのコンピュータ利用のドキュメントにはこのツールのループが書かれていて、1ターンに複数の動作をまとめる方法や、文脈に残す古いスクリーンショットの数を管理する方法も載っています。

マクロは記録時のクリック位置を保存します。エージェントは実行時に見たものから位置を決めるので、ボタンが動いても新しい位置になるだけです。ウェブのテストツールも同じ結論に達しています。Playwrightは、ページの構造に結びついたCSSやXPathのパスではなく、役割と見えるテキストで要素を探すよう勧めています。

先に見ることで動いたボタンには対応できますが、観測が悪いことには何もできません。視覚のステップが「Save」の場所を読み違えれば、エージェントは間違った場所をクリックし、確認がなければそれでも「完了」と報告します。

## クリックのたびの確認は何を加えるのか
動作のたびに、確認するボットはもう一度観測し、画面を期待する変化と比べます。パネルが開いたか、トグルがOnと読めるか、欄に名前が入っているか、状態がSavedと読めるか、です。変化がなければ、もう一度見て、ステップが実は終わっているなら再試行を飛ばし、対象が見えるなら1回だけ再試行し、それ以外なら止まって失敗したと言います。

- 再試行の前に見ること。トグルは冪等ではありません。最初のクリックが効いていて、確認がそれを読み違えた場合、考えなしの2回目のクリックはダークモードをまたオフにしてしまいます。私たちのボットは画面を読み直し、目標がすでに表示されているなら再試行を飛ばします。
- 再試行に上限を付けること。ステップあたり1回の再試行で、混乱したエージェントがいつまでもクリックし続けるのを防ぎます。バックエンドのクライアントが再試行とバックオフで守っているのと同じ規則です(Amazon Builders' Libraryの記事が、際限のない再試行が失敗をどう増幅するかを説明しています)。

## 私たちが実行したとき
2026-11-06に[`node labs/ai-14/run.mjs`](https://github.com/systemdesignsimple/labs/blob/main/labs/ai-14/run.mjs)を実行しました。ラボでは、Saveボタンかダークモードのトグルが動いた50回(うち8回はポップアップ付き)に、動かない10回のコントロールを加えて回します。観測はすべてページの状態からシミュレーションし、エラーを混ぜています。ブラウザもスクリーンショットもOCRも使いません。

リプレイボットは動いた50回中2回終え、終えていない48回でも「完了」と言いました。見るだけで確認しないボットは50回中43回終え、黙った失敗は4回でした。動作のたびに確認するボットは50回中47回終え、黙った失敗は0回で、届かなかった3回はあきらめてそう報告しました。コントロールでは意外な結果が出ました。何も動いていないのに、確認するボットは10回中8回しか終えられず、動いた50回では正しいコントロールに当たったクリックのあとに確認が15回誤報を出しました。1タスクあたりの時間も、リプレイの2.4秒に対して13.83秒(シミュレーション上の時間)でした。つまりこの50回では、確認がすべての失敗を見えるようにしました。ただ、確認そのものも、信頼する前に自分のテストが必要です。

私たちのラボは、このページが説明するループをシミュレーションしています。エージェントが観測を頼んで次の動作を決め、アプリケーションが実行して見たものを返します。

## 具体例
私たちのラボは、メモリ上の400 x 700 pxの設定ページで、4つのステップがあります。設定を開く、ダークモードをオンにする、Calm Rと名前を入力する、Saveを押す、です。成功を決めるのはページ自身で、dark = onと正しい名前が保存されていなければなりません。50回ではSaveかトグルがランダムな空き場所に動き、うち8回はポップアップがその上にありました。

```text
moved runs (50)              finished   silent fail   noticed fail   time per task
replay recorded clicks        2 (4%)        48             0            2.4 s
look, act                    43 (86%)        4             3            8.07 s
look, act, check             47 (94%)        0             3           13.83 s

assumed costs: observation 1,300 ms, click 150 ms, settling 300 ms, typing 600 ms
13.83 / 2.4 = 5.76, about 6x the simulated time of replay
look, act, check: 47 finished + 3 reported = 50, so every failure was reported
unchanged page (separate 10 runs): replay 10/10, look 6/10, look + check 8/10
```

動かないレイアウトでは、リプレイは10回すべて速く終えました。見るボットは、混ぜた観測エラーのせいでそこで回数を落とし、確認が8回まで持ち直しました。

見るボット2つは同じシードから始めますが、確認がランダムな抽選を消費するので、確認するボットの最初の確認のあと、2つのボットは違う観測を受け取ります。1回ずつではなく、合計で比べてください。2つの差は、このシミュレーターのこの想定コストとエラー率のもとでのもので、本番で改善を測ったものではありません。

## コード
確認を入れるには、動作のたびに検証を加え、再試行の前に目標を確認します。[`labs/ai-14/run.mjs`](https://github.com/systemdesignsimple/labs/blob/main/labs/ai-14/run.mjs)のステップループです(ポップアップの処理は省いています)。

```js
// labs/ai-14/run.mjs (trimmed: popup dismissal omitted)
for (const g of GOALS) {                       // Settings, Dark mode, Name, Save
  let ok = false, attempts = 0;
  while (!ok && attempts < 2) {                // one try plus one bounded retry
    const s = look();                          // observe: labels and positions
    if (check && attempts > 0 && verdict(s, g.done)) { ok = true; break; } // already done: do not click again
    attempts++;
    const target = s.find((i) => (g.match ? g.match(i.text) : i.text === g.label));
    if (!target) continue;                     // label not seen: look again on the next pass
    const hit = click(target.x, target.y);
    if (g.type) { steps++; t += COST.type; page.type(g.type); } // step 3 types "Calm R"
    ok = check ? judge(hit, g.intend, g.done, g.label) : true;  // the no-check bot assumes success
  }
  if (!ok) return out(false, g.label);         // stop and say where it failed
}
```

`g.match`がトグルでは大事です。ラベルは「Dark mode Off」か「Dark mode On」と読めるので、目標は「Dark mode」で始まるラベルなら何でも合います。[`labs/ai-14`](https://github.com/systemdesignsimple/labs/tree/main/labs/ai-14)で`node run.mjs`を実行してください(Node 22、パッケージ不要)。上の表と、きれいに終わらなかったすべての実行のページログを出します。move-14では、Saveのクリックが空のパネルに当たり、確認がそれをとらえ、次の観測でSaveのラベルを見落とし、ボットは成功を主張せずにSaveのところであきらめました。

## 失敗の形と例外
- 確認が読み違える。確認も同じノイズのある観測を使い、さらに3%の確率で独自に判定を反転させます。確認するボットは、正しいコントロールに当たったクリックのあとに15回確認を失敗させましたが、ページ自身の真実から見れば15回すべて誤報でした。再試行の前に見る規則が、それらを二重クリックにしませんでした。
- 確認が失敗を合格にする。確認が「完了」と言っても、ステップが失敗していることがあります。ここでは間違ったクリック7回をすべてとらえましたが、このサンプルで黙った失敗が0回だからといって、それが起きないとは言えません。
- ステップが一度も確認されない。3回は、必要なステップを確認せずに終わりました。move-27では、トグルのクリックは効いたのに、その後の観測で成功を確認できませんでした。ボットは止まって報告しました。それが求める動きです。
- 同じラベルが2つ。私たちのボットはラベルの文字で合わせます。「Save」が2つあるボタン、アイコンだけのコントロール、言い換えられたラベルには、役割やダイアログ内の位置、近くの見出しといった文脈が要ります。
- ポップアップ。動いたボタンの上にポップアップがあると、クリックは通りません。見るボット2つはどちらもポップアップを消して、8回のポップアップ実行をすべて終えました。リプレイは1回も終えられませんでした。

## トレードオフ
| 手法 | 向いていること | 代償 | 使う場面 |
| --- | --- | --- | --- |
| 位置をリプレイする | 速さ、固定レイアウト | レイアウトが変わると黙って失敗する | 画面が決して変わらず、結果を別に確かめられる |
| 見て、動く | 動いた・新しいレイアウト | 観測の時間、間違ったクリックに気づけない | 間違った結果をあとで安く見つけられる |
| 見て、動いて、確認する | この50回のシミュレーションで黙った失敗0回 | シミュレーション上で約6倍の時間、誤報 | 間違った「完了」がお金や信頼を損なう |

## よくある間違い
| 間違い | 代わりにすること |
| --- | --- |
| エージェント自身の「完了」を信じる | 画面の期待する変化を確かめる。できれば保存された状態を確かめる |
| トグルを考えなしに再試行する | まず見る。目標がまだないときだけ再試行する |
| 際限のない再試行 | ステップごとに決まった回数にして、回数を使い切ったら人が引き継げるようはっきり失敗を報告する |
| 記録したレイアウトだけでテストする | ここでの50回の動いた実行のように、わざと動かして試す |

## 練習問題

**[初級] リプレイボットは、失敗した48回すべてでなぜ「完了」と報告したのですか?**

ページを一度も観測しないので、クリックが空きスペースに当たったことに気づけないからです。

**[中級] 確認するボットは、再試行の前に何を見るのですか?**

ステップがすでに終わっているかもしれないからです。トグルをもう一度クリックすると、元に戻してしまいます。

**[中級] 確認なしで見るだけのボットは、動かないページでなぜ6/10なのですか?**

混ぜた観測エラーが間違ったクリックを起こし、それに気づけないからです。

**[上級] Saveの確認に、画面の代わりに何を確かめますか?**

APIや再読み込みで、保存された設定そのものを確かめます。視覚のエラーを避けられます。

**[上級] 6倍のコストをどう下げますか?**

失敗が問題になるステップだけ確認し、画面全体のスクリーンショットの前にURLの変化のような安い合図を使います。

## さらに読む
- コンピュータ利用ツールのドキュメントは、提供者側から見たスクリーンショットと動作のループを説明しています。
- [OSWorld](https://arxiv.org/abs/2404.07972)は、実行ベースのチェックで実際のデスクトップタスクを評価します。私たちの想定した観測エラー率は検証していません。
- Playwrightのロケーターガイドは、テストツールが役割とテキストで要素を探す理由を説明しています。
- 再試行についてのBuilders' Libraryの記事は、上限とバックオフを扱います。
- 私たちのラボ: 実行して、エラー率を変えて、表がどう動くか見てください。チェック役の2つ目のモデルについては、[1つのAIが書き、もう1つがレビューする](https://systemdesignsimple.com/one-ai-writes-one-ai-reviews/)をご覧ください。

私たちのラボは小さなシミュレーションです。AIモデルは動かず、スクリーンショットも撮らず、エラー率と時間コストは私たちの想定です。結果はこのシミュレーションの中でのみ成り立ちます。
