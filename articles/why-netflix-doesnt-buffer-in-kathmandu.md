視聴者が受け取るすべてのバイトは、保存されている場所から運ばれてきます。だから、動画を遠くのデータセンター 1 か所にだけ置けば、チャンクごとに長い往復を払うことになり、バッファの小さいプレイヤーは止まります。コンテンツデリバリーネットワークはコピーを視聴者の近くへ移しますが、CDNのプッシュとプル、つまりコピーを求めに応じて引くのか、事前に押し出すのかで、新しいコンテンツの最初の視聴者が今も待つかどうかが決まります。答えられるようになりたい問いはこうです。ストリーミングサービスは、あなたが再生ボタンを押す前に、なぜ動画をあなたの近くへコピーしておくのか。


## 前提知識
**往復時間と、距離が勝つ理由。** 往復時間(RTT)とは、小さなリクエストがサーバーに届き、返信が戻ってくるまでの時間です。光ファイバー中の光は 1 ミリ秒でおよそ 200 km 進みますが、実際の経路は直線より長いため、別の大陸にあるサーバーはどれだけ速くても往復に数百ミリ秒かかります。[DNSの前回記事](https://systemdesignsimple.com/you-type-google-com-100-ms/)では、名前解決が往復時間の合計だと見ました。コンテンツの取得も同じで、海を越えなければならないリクエストはすべて海の分を払います。

**レイテンシは帯域ではありません。** 太いパイプは 1 秒あたり多くのバイトを運べますが、最初のバイトが早く届くわけではありません。プレイヤーには画質のための帯域と、開始時間のためのレイテンシが必要です。[レイテンシとスループットの記事](https://systemdesignsimple.com/ten-lanes-still-slow/)で違いを説明しました。この記事は主にレイテンシの話です。

**キャッシング。** キャッシュは、必要なものの近くにコピーを置き、コピーが古くなったら使わないというルールを持つ仕組みです。[1 つのデータベースが書き込み、10 の読み取り](https://systemdesignsimple.com/one-database-writes-ten-read/)で出てきた読み取りレプリカはデータベースのキャッシュです。DNSリゾルバも名前をキャッシュします。CDNはファイルや動画をキャッシュします。

## 定義
**オリジンサーバー**: コンテンツの正本を持つサーバー(またはストレージバケット)。他のすべてのコピーはここから作られます。

**エッジサーバー**: 視聴者の近く、多くの場合インターネットプロバイダーのネットワークの中や隣に置かれたキャッシュサーバー。コピーを持っていれば、そこからリクエストに答えます。

**CDN(コンテンツデリバリーネットワーク)**: 多くの場所に置かれたエッジサーバーのネットワークと、各視聴者を近くのサーバーへ送るルーティングの組み合わせです。仕事は 2 つで、視聴者のレイテンシを下げることと、オリジンの負荷を下げることです。

**キャッシュヒットとキャッシュミス**: ヒットとは、エッジが自分のコピーからリクエストに答えることです。ミスとは、エッジがそのものを持っていない(または古い形でしか持っていない)リクエストで、まず上流から取り寄せなければなりません。

**プルCDN**: エッジが、初めてミスしたリクエストでオリジンからオブジェクトを取り寄せて保存し、その後のリクエストにはそのコピーから答えます。オリジンは特別なことをしません。エッジが引きます。

**プッシュCDN(プロアクティブキャッシング、キャッシュウォーミング)**: 誰かが頼む前に、アップロードや運用者が予定したフィルジョブで、コンテンツをエッジのストレージへコピーしておく方式です。

**キャッシュヒット率**: ヒットを全リクエストで割った値です。バイトヒット率は同じ計算をバイトで行います。動画ではオブジェクトが大きいため、こちらが重要になります。

**TTFB(初回バイトまでの時間)**: リクエストを送ってから応答の最初のバイトを受け取るまでの時間です。ネットワークの往復とサーバーの処理を含みますが、残りの本体をダウンロードする時間は含みません。

**セグメント(チャンク)**: 動画を切った短い断片で、たいてい数秒分です。普通の HTTP オブジェクトとして配信されます。HLS も MPEG-DASH もこうして動画を切り、セグメントをプレイリストやマニフェストに並べるため、普通の HTTP キャッシュが動画を配信できるのです。

## 仕組み: エッジを通る 1 回のリクエスト
プレイヤーは 1 つの巨大なファイルをダウンロードしません。まずマニフェスト([RFC 8216](https://www.rfc-editor.org/rfc/rfc8216)で定められた HLS プレイリスト、または DASH の MPD)を取り寄せます。そこにはセグメントが並んでいて、セグメント 1、セグメント 2 と、1 つずつ HTTP GET で取り寄せます。各セグメントはただの URL で、その裏にバイトがあります。だから、どんな HTTP キャッシュでもセグメントを保存できます。これが、CDNが動画に使える理由です。

プルエッジを通る 1 回のセグメントリクエストは、こう流れます。

1. **ルーティング。** DNS やエニーキャストがプレイヤーを近くのエッジへ向けます。そのエッジの裏では、[ロードバランサーやリバースプロキシ](https://systemdesignsimple.com/load-balancer-vs-reverse-proxy/)がリクエストを複数のキャッシュサーバーへ振り分けることがよくあります。
2. **キャッシュキー。** エッジはリクエストからキーを作ります。ふつうはホストとパスで、選んだヘッダーやクエリパラメーターを加えることもあります。
3. **検索。** キーがキャッシュにあり、コピーが新鮮ならヒットです。エッジはバイトをそのまま流し返します。コストは短い往復 1 回と、少しのサーバー処理だけです。
4. **ミス。** キーがなければ、エッジはオリジンへの接続を開く(または再利用する)してオブジェクトを頼み、最初のバイトが長い経路を越えてくるのを待ちます。
5. **フィル。** バイトが届くにつれて、エッジはそれをキャッシュ(メモリまたはディスク)へ書き込みながら、プレイヤーへ転送します。書き込み、索引付け、場合によっては別のオブジェクトの追い出しにも時間がかかります。私たちのラボではこれをミス処理と呼びます。
6. **再利用。** 同じキーを頼む次の視聴者はヒットになります。

*私たちのモデルでは、エッジサーバーは視聴者から約 10 ms の場所にあります。こうしたエッジがたくさん集まって CDN になります。*

ミスが何を払うのか、よく見てください。「ファイルが遠い」だけではありません。視聴者はエッジまでの短い区間を払い、エッジはオリジンまでの長い区間を払い、さらにオリジン自身のサーバー処理と、エッジの検索と保存の作業も払います。だから、その 1 回のリクエストだけなら、プルエッジはオリジンへ直接行くよりわずかに遅くなることがあります。得になるのは、同じオブジェクトへの 2 回目のリクエストからです。

### プレイヤーはその時間をどう使うか

プレイヤーは、ダウンロード済みで未再生のメディアをバッファにためます。バッファが 0 まで減ると、停止(再バッファリング)が起きます。一般にバッファ量 B はこう変化します。

```text
dB/dt = (delivery rate / media bitrate) − 1      (seconds of media gained per second, while playing)
stall when B reaches 0
```

つまり停止は、バッファに何秒分のメディアがあるかと、ビットレートに対する持続的な配信速度で決まります。1 回のリクエストのレイテンシだけでは決まりません。私たちのラボでは、わざと単純化した版を使います。プレイヤーは各セグメントを、期限の 300 ms 前という固定のリードタイムで頼みます。

```text
lab rule:  stall if   TTFB + transfer time  >  lead time (300 ms)
```

これで、リクエストごとのレイテンシが見えるようになります。これがこのモデルの狙いです。実際のプレイヤーは何秒分ものバッファを持つため、定常再生では数百ミリ秒の TTFB で止まることはめったにありません。

起動はレイテンシが最も見えるところですが、1 回のセグメント取得より部品が多いです。マニフェストの取得、あれば DRM ライセンス、初期化セグメント、それからメディア、転送、デコーダーの開始があります。私たちのラボが報告するのは、**再生が最初のセグメント全体を待つと仮定した、モデル上の起動時間**です。セグメント 1 の TTFB に転送時間を足したものです。プログレッシブ配信を使うプレイヤー(たとえば部分セグメントや CMAF チャンクをデコードする低遅延モード)は、セグメント全体が届く前に再生を始められます。だからラボの数字は、1 つの部品のモデルとして扱ってください。計測された開始時間ではありません。

## CDNのプッシュとプル: 埋めるのは誰か
違いは、コピーを作るきっかけが誰にあるかです。

**プル**設計では、視聴者のリクエストがきっかけです。誰かが頼むまで何も保存されないため、キャッシュには人々が実際に見るものだけが入ります。計画は要りません。代償はコールドミスです。各オブジェクトの最初の視聴者は各エッジで長い往復を払い、新しいエピソードに多くの人が同時に再生ボタンを押せば、オリジンには一度に大量のリクエストが届きます。

**プッシュ**設計では、運用者がきっかけです。フィルジョブが選んだコンテンツを、頼まれる前にエッジへコピーします。できれば回線が空いている時間にやるため、最初の視聴者も 100 人目と同じ速さになります。代償はストレージと予測です。誰も見ないバイトをプッシュすれば、ディスクも転送も無駄になります。

![チャンク 1、2、3 のフィルムストリップが長い道を上がり、PUSH の区画へ落ちる。区画は緑色に光り、準備完了のタグが付いている。上のほうでは月のアイコン付きの暗い電話が待っている](https://systemdesignsimple.com/img/why-netflix-doesnt-buffer-in-kathmandu/b04.webp)
*プッシュ: 選んだチャンクは、近くで誰かが再生ボタンを押す前にエッジへ置かれます。*

Netflix は自社の CDN について、関連する事実を 1 つ公開しています。[Open Connect 概要](https://openconnect.netflix.com/Open-Connect-Overview.pdf)によると、コンテンツは事前に Open Connect アプライアンスへ置かれます(プロアクティブキャッシング)。多くはオフピーク時間帯に行われます。これが、ネットワークが静かな時間に合わせたプッシュです。私たちは彼らのシステムの他の内部詳細を何も説明しません。この記事のそれ以外はすべて、典型的な設計の話です。

人気が偏っている場合、ハイブリッドも 1 つの選択肢です。少数の先頭タイトルやファイルがリクエストの大きな割合を取り、長い裾の部分はそれぞれ少しずつしか頼まれません。

- **先頭部分をプッシュする。** 人気が予測できるコンテンツ(新作、ランディングページ、ゲームのパッチ)は、フィルウィンドウの間にエッジへ事前に配置します。
- **裾の部分をプルする。** それ以外は求めに応じて取り寄せ、使われている間は保持し、場所が必要になれば追い出します(Nginx はたとえば、キャッシュが `max_size` を超えると最も使われていないデータを削除します)。
- **タイトル内で先読みする。** プルエッジは、セグメント N が頼まれたときにセグメント N+1 を取り寄せることができます。次のリクエストがヒットになるのは、プレイヤーが実際に選ぶ画質(ビットレート)をエッジが当て、プレイヤーが頼む前に先読みが終わり、オリジンと回線に余裕があり、頼まれたときにオブジェクトがまだ残っている場合だけです。適応ビットレートでは、画質の予想が外れれば先読みは丸ごと無駄なフィルになります。

本当の問いは、大事なコンテンツの各エッジでの最初のリクエストを、最も安くヒットにする方法です。

### プッシュはいつ得になるか: 損益分岐の例

1 つのエッジでの 1 つのオブジェクトへのリクエストを、レート λ のポアソン過程としてモデル化します。T を滞在ウィンドウ(プルしたコピーが追い出されたり期限切れになったりするまでの時間)とします。ウィンドウあたり 1 回のフィルを仮定し、プッシュとプルでオブジェクトのサイズ S は同じとします。すると次のようになります。

```text
P(pull fetches the object in a window) = 1 − exp(−λT)
expected pull bytes per edge per window = S × (1 − exp(−λT))
push bytes per edge per window          = S                    (pushed whether or not anyone asks)
push / pull byte ratio                  = 1 ÷ (1 − exp(−λT))
```

計算例です。

```text
λT = 0.1  → 1 − e^−0.1 = 0.0952   → 9.52% of edges ever request it   → push moves ≈ 10.5× the pull bytes
λT = 1    → 1 − e^−1   = 0.632    → push moves ≈ 1.58×
λT = 3    → 1 − e^−3   = 0.950    → push moves ≈ 1.05×
```

つまり、ウィンドウあたりエッジごとに約 3 回頼まれるタイトルなら、プッシュのフィルバイトはほとんど余計にかからず、各エッジでの最初の視聴者のコールドミスも消えます。λT = 0.1 の裾のタイトルでは、すべてのエッジへプッシュすると、プルの約 10.5 倍の転送とストレージを使います。それで救えるのは、視聴者が現れる約 9.5% のエッジでの 1 回のミスペナルティだけです(私たちのモデルでは、起動時間のモデル値が 335 ms から 75 ms になります)。余計なバイトを、オフピークの転送とエッジディスクの値段で測り、最初のリクエストのレイテンシの価値と比べてください。このモデルは、ウィンドウ内での人気の変化、部分的なフィル、プッシュ時の失敗を無視しています。配置の目安であって、予測ではありません。

## HTTPキャッシュのルールはCDNをどう制御するか
プルエッジは HTTP の共有キャッシュで、共有キャッシュのルールは [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111) にあります。オリジンは主にレスポンスヘッダーを通じてエッジを制御します。

**鮮度。** 保存されたレスポンスは、その年齢が鮮度有効期間を下回っている間は新鮮です。有効期間は `Cache-Control: s-maxage`(共有キャッシュだけに効きます)から来ます。なければ `max-age`、なければ `Expires` ヘッダー、なければヒューリスティックです。式にすると次の通りです。

```text
fresh  if  current_age < freshness_lifetime
freshness_lifetime = s-maxage, else max-age, else (Expires - Date), else heuristic
```

**Age。** キャッシュが保存されたレスポンスを出すとき、`Age` ヘッダーを送ります。オリジンでレスポンスが生成されて、または最後に検証されてからの経過時間の見積もりで、単位は秒です。[RFC 9111、4.2.3 節](https://httpwg.org/specs/rfc9111.html#age.calculations)によると、上流の `Age` 値、見かけの年齢(`max(0, response_time − date_value)`)、リクエストの転送遅延の補正(`response_delay`)、そしてコピーがローカルに置かれていた時間から計算します。

```text
corrected_initial_age = max(apparent_age, age_value + response_delay)
current_age           = corrected_initial_age + resident_time
```

だから `Age: 0` はミスを証明しません。フィルや再検証から 1 秒以内に出された新鮮なヒットも 0 を示します。診断するには、キャッシュ自身のステータスを記録してください(Nginx では `$upstream_cache_status`: `MISS`、`HIT`、`EXPIRED`、`STALE`、`UPDATING`、`REVALIDATED`、`BYPASS`)。RFC に沿って `Age` を出すキャッシュでは、数秒間にわたるヒットを繰り返すと年齢が増えていくはずです。ただし下の Nginx の例では当てはまりません。増えていく `Age` を出す設定になっていないため、ヘッダーがないことや変わらないことはキャッシュの故障ではありません。代わりに `X-Cache-Status` とアクセスログを使ってください。

**再検証。** コピーが古くなっても、キャッシュがいつもダウンロードし直すわけではありません。保存した `ETag` を使って `If-None-Match` を付けた条件付きリクエストや、`If-Modified-Since` を送ることができます。オリジンが `304 Not Modified` と答えれば、長い経路を越えるのはヘッダーだけで、保存した本体を再利用できます。

**古いものを出す。** `stale-while-revalidate` と `stale-if-error` の拡張(RFC 5861 で定義され、[MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control) に説明があります)により、キャッシュは少し古いコピーで答えながら裏で更新したり、オリジンが壊れている間は古いコピーで答えたりできます。視聴者はヒット並みの速さで答えを受け取り、更新は誰も待たせずに長い往復を払います。

**private と no-store。** `private` は共有キャッシュへの保存を禁じます(1 人のユーザー向けのものです)。`no-store` はどこへのキャッシュも禁じます。個人のページ、アカウントのデータ、署名付き URL はたいていここに当てはまります。

動画では、こうしてきれいに分かれます。

| オブジェクト | 典型的なヘッダー | 理由 |
| --- | --- | --- |
| バージョン付き URL の動画セグメント | `Cache-Control: public, max-age=31536000, immutable` | その URL の裏のバイトは決して変わらないため、キャッシュは新鮮な間は保存したレスポンスを再利用でき、更新時に無効化する必要がありません |
| オンデマンドのマニフェスト | セグメントと同じく長い `max-age` でバージョン付き | セグメントの一覧はエンコードが終われば固定されます |
| ライブのマニフェスト | 1 セグメント分程度かそれ以下の `max-age` | 新しいセグメントが数秒ごとに現れます。古いプレイリストではプレイヤーが遅れます |
| 個人の API(視聴履歴、アカウント) | `private` または `no-store` | 他の人に決して出してはいけません |

最初の行の裏技は、内容ではなく URL を変えることです。変わったファイルは新しい名前(パスにハッシュやバージョン)で公開し、何もパージする必要はありません。ただしこれで避けられるのは更新による無効化だけです。コールドリクエスト、追い出し、有効期限、新しいエッジによるフィルは今も起きます。

## ヒット率、オリジン負荷、階層キャッシュ
ヒット率を h とすると、エッジでの TTFB の期待値は加重平均になります。オリジン負荷の式は、単純な 1 段のモデルでのみ成り立ちます。リクエストの合流なし、再検証なし(`304` もオリジンへのリクエストですが本体は運びません)、ウォームアップなし、シールドなしの場合です。

```text
E[TTFB] = h × TTFB_hit + (1 − h) × TTFB_miss
origin requests per second ≈ (1 − h) × edge requests per second   (single tier, no coalescing)
```

私たちのモデルの平均値、ヒット 15 ms、ミス 273 ms を入れてみます。

```text
h = 0.90 → 0.90 × 15 + 0.10 × 273 = 13.5 + 27.3 = 40.8 ms
h = 0.99 → 0.99 × 15 + 0.01 × 273 = 14.85 + 2.73 = 17.58 ms
```

ヒット率が 90% から 99% へ上がると、平均は半分以下になり、オリジンへのトラフィックは 10 分の 1 になります。リクエストの 10% から 1% へです。だから運用者は最後の数パーセントを追います。オリジンと長い回線は高価で共有の部分であり、[1 人には速いシステムが 100 万人には遅い理由](https://systemdesignsimple.com/fast-alone-slow-crowded/)で見た通り、キューができるのはミスのところです。

平均は裾を隠しますが、裾がどこに出るかは正確に言えます。この 2 点モデル(99% のリクエストが 15 ms、1% が 273 ms)では、逆累積分布関数の定義(パーセンタイル p とは、F(x) ≥ p を満たす最小の x)を使うと、p99 は **15 ms** です。ちょうど 99% のリクエストがそれ以下だからです。一方 p99.9 は **273 ms** です。ヒット率を 98.9% まで下げると、p99 は 273 ms へ跳ねます。つまり目標ヒット率の近くでは p99 は不安定で、ミスのコストを確実にさらけ出すのは p99.9 です。

### オリジンシールドと階層キャッシュ

エッジが 1,000 個あって、それぞれが新しいオブジェクトを独立に引くと、オリジンには同じバイトへのリクエストが 1,000 件届くことがあります。**オリジンシールド**(階層キャッシュ、リージョナルキャッシュともいいます)は、もう 1 段のキャッシュ層を間に入れます。エッジのミスはシールドへ行き、シールドのミスだけがオリジンへ行きます。

```text
miss at edge, hit at shield:  TTFB ≈ RTT(viewer→edge) + RTT(edge→shield) + server times
miss at both:                 TTFB ≈ RTT(viewer→edge) + RTT(edge→shield) + RTT(shield→origin) + server times
origin fills per object       ideally one successful fill per cache key per shield per residency period
                              (with effective request coalescing), instead of one per edge
```

これは理想であって、上限ではありません。有効期限が切れれば新しい滞在期間が始まり、追い出されれば再フィルが必要になり、フィルが失敗すれば(オリジンのエラーやタイムアウト)リトライされ、合流を逃れた同時ミスはそれぞれ上流へ行きます。シールドはフルミスに 1 ホップ加えますが、オリジンを守り、多くのエッジミスをより短いシールドヒットに変えます。私たちのラボではシールドをモデル化していません。この式は、シールドが何を加えるかを示しています。

### リクエストの合流

シールドとエッジにはもう 1 つの問題があります。バーストです。人気のオブジェクトが期限切れになったり初めて現れたりすると、多くのリクエストが同じ瞬間にミスすることがあります。何もしなければ、それぞれが自分のオリジンへの取り寄せを始めます。これをキャッシュスタンピード、サンダリングハードといいます。**リクエストの合流**(コラプストフォワーディング)では、最初のミスが取り寄せている間、他のリクエストはその同じ取り寄せを待ちます。Nginx では [`proxy_cache_lock on`](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_lock) がこれです。Varnish は同じオブジェクトへのリクエストをデフォルトで合流します。

Nginx のロックには時間の上限があり、その上限がどれだけ効くかを決めます。`proxy_cache_lock_timeout 5s`(デフォルト)では、ロックを 5 秒待ったリクエストはオリジンへ行ってしまい、そのレスポンスはキャッシュされません。別に、`proxy_cache_lock_age 5s` により、進行中のフィルが 5 秒以内に終わらなければ、もう 1 件のリクエストが上流へ行きます。つまり、大きなセグメントの配信に 5 秒以上かかる遅いオリジンでは、合流したバーストが再び複数のオリジンリクエストに戻ります。最良の場合、バースト全体にオリジンへのリクエストは 1 件で済みます。遅いオリジンや壊れたオリジンでは、もっと増えることを想定し、1 件だと決めつけずにキーごとの上流リクエスト数を監視してください。

## 計算例
動画のシナリオです。カトマンズの視聴者が新しいエピソードの再生ボタンを押します。3 つの構成を比べます。これらは仮想クロック上の決定的モデル用に私たちが選んだ遅延で、どのネットワークや Netflix の計測でもありません。

- **オリジンだけ:** 視聴者は往復 250 ms と仮定したオリジンと話します。これは遠いオリジンを表すために私たちが選んだ入力で、計測された経路ではありません。
- **プルエッジ:** 10 ms 先と仮定したエッジで、最初は空です。ミスすると 240 ms 先のオリジンへ行き、検索と保存に 15 ms を使います。
- **プッシュエッジ:** 同じエッジで、20 チャンクすべてが再生前に置かれています。

どのサーバーもチャンクを探すのに 5 ms を使い、どの経路でも本体の転送に 60 ms かかります(つまり帯域は同じです)。各ホップには ±10% のジッターがあり、エピソードは 2 秒のチャンク 20 個で、プレイヤーは各チャンクを期限の 300 ms 前に頼みます。各構成を 3 回実行しました(シード 11、22、33)。ジッター表は構成間で共通で、最初の視聴者のあと、2 番目の視聴者が同じエッジ経由で見ました。

```text

             server 5, transfer 60, jitter ±10%, lead 300, 20 chunks × 2 s

TTFB, expected without jitter:
  origin only     250 + 5                     = 255
  pull miss       10 + 15 + 240 + 5 + 5       = 275    (edge hop, miss work, origin hop, two servers)
  hit (pull/push) 10 + 5                      = 15

modeled startup = TTFB(chunk 1) + transfer 60   (assumes playback waits for the complete first segment):
  origin only     255 + 60 = 315 expected  → model 318 ms
  pull, viewer 1  275 + 60 = 335 expected  → model 335 ms
  push, viewer 1   15 + 60 =  75 expected  → model 75 ms
  pull, viewer 2   15 + 60 =  75 expected  → model 75 ms

stall check (lab rule): chunk needs TTFB + 60 < 300 lead
  origin  254 + 60 = 314 > 300 → late on most chunks   → 16 stalls, 282 ms rebuffering
  pull v1 273 + 60 = 333 > 300 → late on every chunk   → 19 stalls (of 19 after the first), 628 ms
  hits     15 + 60 =  75 < 300 → 225 ms of slack       → 0 stalls

Averages over 3 runs (model):
  setup / viewer   startup       mean TTFB   stalls   edge hit rate
  origin only        318 ms        254 ms      16          -
  pull, viewer 1     335 ms        273 ms      19          0%
  pull, viewer 2      75 ms         15 ms       0        100%
  push, viewer 1      75 ms         15 ms       0        100%
```

表は 3 段階で読んでください。まず、プルエッジは最初の視聴者を助けませんでした。ヒット 0%、起動時間のモデル値はオリジンより 17 ms 遅い 335 ms(318 ms に対して)、停止も 19 回で 16 回より多いです。各ミスがエッジへのホップ、ミス処理、もう 1 回のサーバー遅延を加えるからです。次に、そのミスがキャッシュを埋めたため、視聴者 2 は 75 ms で停止 0 回でした。最後に、プッシュエッジは最初の視聴者から 75 ms を出しました。帯域が同じなのに差が出るのは、チャンクがどこに置かれていたかと、プルのミスコストのせいです。

## コード
最初のスニペットは、ラボのエッジキャッシュを切り詰めた版です。固定の遅延、ジッターなし、チャンク 1 個、仮想クロック(数字を足すだけ)です。`edge_cache.mjs` として保存し、Node.js 18 以降で `node edge_cache.mjs` と実行してください。パッケージもネットワークも要りません。

```js
// edge_cache.mjs: origin vs pull vs push on a virtual clock (fixed delays we chose, no network)
const D = { originRtt: 250, edgeRtt: 10, edgeToOrigin: 240, missOverhead: 15, server: 5, transfer: 60 };

class Origin {
  constructor() { this.requests = 0; }
  fetch() { this.requests++; return D.originRtt + D.server; }   // time to first byte, ms
}

class EdgeCache {
  constructor(origin) { this.origin = origin; this.store = new Set(); this.hits = 0; this.misses = 0; }
  prefill(ids) { for (const id of ids) this.store.add(id); }      // push: copy in before anyone plays
  fetch(id) {
    if (this.store.has(id)) { this.hits++; return D.edgeRtt + D.server; }   // HIT: short hop only
    this.misses++;                                                          // MISS: pull from origin
    this.origin.requests++;
    this.store.add(id);                                                     // keep it for the next viewer
    return D.edgeRtt + D.missOverhead + D.edgeToOrigin + D.server + D.server;
  }
}

const firstFrame = (path) => path.fetch(0) + D.transfer;   // chunk #1 only

console.log("origin only     ", firstFrame(new Origin()), "ms");

const pull = new EdgeCache(new Origin());
console.log("pull, viewer 1  ", firstFrame(pull), "ms");
console.log("pull, viewer 2  ", firstFrame(pull), "ms");

const push = new EdgeCache(new Origin());
push.prefill([0, 1, 2]);                                    // done earlier, off-peak, in a real system
console.log("push, viewer 1  ", firstFrame(push), "ms");
console.log("origin requests at play time: pull", pull.origin.requests, "| push", push.origin.requests);

// Coalescing: 100 viewers ask for the same cold chunk in the same instant.
function burst(n, coalesce) {
  const origin = new Origin();
  const inFlight = new Map();                               // chunk id -> fetch already running
  for (let i = 0; i < n; i++) {
    if (coalesce && inFlight.has(7)) continue;              // join the running fetch
    inFlight.set(7, origin.fetch(7));
  }
  return origin.requests;
}
console.log("cold burst of 100: origin requests", burst(100, false), "without lock,", burst(100, true), "with lock");
```

何を見るかです。

```text
origin only      315 ms
pull, viewer 1   335 ms
pull, viewer 2   75 ms
push, viewer 1   75 ms
origin requests at play time: pull 1 | push 0
cold burst of 100: origin requests 100 without lock, 1 with lock
```

ジッターがなければ、オリジンの行は期待値の 315 ms です。フルラボは ±10% のジッターを加えて 3 回実行し、平均して 318 ms になります。プルの行は、1 つのチャンクでの「ミスしてからヒット」を示し、プッシュエッジは再生時にオリジンへ何も送りませんでした。`missOverhead` を 0 にすると、最初のプル視聴者は 320 ms になります。それでも 315 ms より遅いのは、エッジへのホップとサーバー遅延が余計にかかるからです。合流の行は理想のケースで、バーストが瞬時に起き、フィルが失敗もタイムアウトもしない場合です。下の Nginx の節で、実際のロックがどんなときに余計なリクエストを通すかを示します。フルラボ([`labs/sd-14/run.mjs`](https://github.com/systemdesignsimple/labs/blob/main/labs/sd-14/run.mjs))は 20 チャンクすべてを再生して停止を数えます。

同じ考えを実際のキャッシュで表すと、こうなります。この設定は、Nginx を合流と古いものの提供ができる小さなプルエッジにします([プロキシモジュールのドキュメント](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)のディレクティブです)。

```nginx
# edge.conf: Nginx as a pull cache in front of a faraway origin
proxy_cache_path /var/cache/edge levels=1:2 keys_zone=video:100m
                 max_size=50g inactive=7d use_temp_path=off;

server {
    listen 80;

    location /video/ {
        proxy_pass https://origin.example.com;
        proxy_cache video;
        proxy_cache_key "$scheme$proxy_host$request_uri";   # the default: keeps the full query string
        proxy_cache_valid 200 206 7d;               # fallback lifetime; upstream cache-control headers take precedence

        proxy_cache_lock on;                        # coalesce concurrent misses for the same key
        proxy_cache_lock_timeout 5s;                # after 5 s a waiter goes upstream, uncached
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;           # refresh stale copies without making viewers wait

        add_header X-Cache-Status $upstream_cache_status always;   # MISS, HIT, EXPIRED, STALE, UPDATING
    }
}
```

**キャッシュキーはセキュリティの境界です。** 上のキーは[ドキュメントのデフォルト](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_key)である `$scheme$proxy_host$request_uri` で、クエリ文字列を含みます。よくある「最適化」は `$scheme$host$uri` で、クエリパラメーターをすべて落とします。これは危険です。2 つの異なる表現(たとえば `?rendition=1080p` と `?rendition=480p`)が 1 つのキーに衝突します。署名付き URL では、有効な署名を持つリクエストがエントリを埋め、そのあと署名の期限が切れたり署名のないリクエストがキャッシュから出されることになります。署名をチェックするオリジンには二度と聞かないからです。署名をキーに残しても直りません。キャッシュが細かく分かれるだけで、コピーが保存されたあとの期限切れはやはり強制されません。保護されたコンテンツは、キャッシュの検索の**前**に、エッジ自身で認可する必要があります。たとえば [`ngx_http_secure_link_module`](https://nginx.org/en/docs/http/ngx_http_secure_link_module.html) でハッシュと期限をチェックするか、`auth_request` のサブリクエストを使います。クエリパラメーターをキーから外すのは、内容もアクセス制御も変わらないと証明できたあとだけにしてください(`utm_*` のような分析タグがふつうの候補です)。

`curl -sI http://localhost/video/ep1/seg-001.ts` で同じセグメントを 2 回リクエストし、`X-Cache-Status` が `MISS` から `HIT` へ変わるのを確認してください。`curl -w '%{time_starttransfer}\n' -o /dev/null -s <url>` で両回の TTFB を比べると、下がっているのが見えます。プルキャッシュで「プッシュ」するには、ウォームアップします。新しいタイトルの全セグメントを、発表前にスクリプトからリクエストするのです。これがキャッシュウォーミングの最も単純な形です。

## Nginxのキャッシュの仕組みと容量見積もり
上のディレクティブは、特定のライフサイクルを持つストレージエンジンを隠しています。以下の仕組みは、[`proxy_cache_path` のドキュメント](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_path)と [Nginx のキャッシュ実装](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_file_cache.c)に従います。容量の数字は私たちの計算上の仮定です。

**ファイル名はキーの MD5 から来ます。** Nginx はキャッシュキーを MD5 でハッシュし、32 文字の 16 進ダイジェストをファイル名にします。`levels=1:2` は、ハッシュの末尾から 2 段のディレクトリツリーを作ります。最後の 1 文字、次にその前の 2 文字です。ドキュメントの例では、キーのハッシュ `b7f54b2df7773722d382f4809d65029c` が `/data/nginx/cache/c/29/b7f54b2df7773722d382f4809d65029c` に保存されます。ファイルは 16 × 256 = 4,096 個のディレクトリに分散するため、1 つのディレクトリに何百万ものエントリが入ることはありません。

**メタデータは共有メモリにあります。** `keys_zone=video:100m` は、すべてのワーカープロセスから見える共有メモリゾーンを作り、アクティブなキーとエントリごとのメタデータ(有効性、最終アクセス)を保持します。ドキュメントによると 1 メガバイトで約 8,000 キーなので、100 MB で約 800,000 エントリを索引できます。ゾーンの中では、エントリはキャッシュキーの MD5 をキーにした赤黒木に並ぶため、検索は共有メモリで O(log n) です。さらに同じエントリを最終アクセス順に並べたキューがあり、追い出しは冷たいほうから歩きます。ヒットでも、本体の前にディスクへ触れます。Nginx はファイルを開いてヘッダー(フォーマットバージョン、有効期間、キーとキーの CRC32)を読み、エントリを検証します。不一致はミスとして扱われます。ゾーンは `max_size` とは別の容量制限なので、ディスク容量ではなく想定されるオブジェクト数から見積もってください。

**フィルは一時ファイル経由で、最後にリネームします。** 上流からのレスポンスはまず一時ファイルに書かれ、最後にキャッシュへリネームされます。そのため、エントリは本体が完成したときに初めてディスクに現れます。`use_temp_path=off` では、一時ファイルはキャッシュディレクトリ内に書かれるため、リネームは 1 つのファイルシステム内で行われます(コピーではなく安いメタデータ操作です)。

**2 つのヘルパープロセスがライフサイクルを管理します。** **キャッシュローダー**は起動後に 1 回だけ動き、キャッシュディレクトリを歩いてディスク上のファイルから共有メモリのメタデータを再構築します。バッチで処理します(`loader_files`、デフォルトは 1 回あたり 100 ファイル、`loader_threshold` は 1 回あたり最大 200 ms、`loader_sleep` は間の 50 ms)。ディスク上のオブジェクトは、ローダーがまだ処理していなくても失われません。コールドローディング中、共有メモリにエントリが見つからない検索でも、ディスク上のファイルをチェックし、有効なものがあればその場で索引して出します。だから再起動のコストは、余計なファイルシステムの作業(ローダーがまだ到達していないキーについてファイルを開いてヘッダーを読むこと。ローダー自身のディレクトリ走査と競合します)と、多少の起動レイテンシであって、ヒット率が自動的に落ちることではありません。**キャッシュマネージャー**は定期的に動きます。合計サイズが `max_size` を超えたとき(または空き容量が `min_free` を下回ったとき)、最も使われていないデータを削除します。

**鮮度と `inactive` は別の時計です。** 鮮度(オリジンからの `Cache-Control`、なければ `proxy_cache_valid`)は、エントリを上流に聞かずに出せるかを決めます。`inactive` は、エントリがそもそもディスクに残るかを決めます。その時間アクセスがなければ、新鮮かどうかに関係なく削除されます(デフォルトは 10 分)。つまり `proxy_cache_valid 7d` でもデフォルトの `inactive` なら、1 回見られて 11 分放置されたセグメントは、1 週間新鮮なはずなのに消えます。逆に、期限切れでもよくアクセスされるエントリはディスクに残り、安い `304` で再検証できます。上の設定は `inactive=7d` なので、裾のセグメントは視聴者の間隔が空いても残ります。

**容量の計算例。** 6 Mbit/s の画質で 2 秒のセグメントを仮定します。

```text
segment size  = 6 Mbit/s × 2 s ÷ 8 bits per byte   = 1.5 MB
10,000 segments × 1.5 MB                           = 15 GB   (one rendition, 20,000 s ≈ 5.6 h of video)
max_size=50g is binary: 50 GiB = 50 × 1024³        = 53,687,091,200 bytes
53,687,091,200 ÷ 1,500,000 bytes                   ≈ 35,791 segments
53,687,091,200 ÷ 15,000,000,000 bytes              ≈ 3.58 catalogs
keys needed ≈ 35,791  vs  zone capacity ≈ 800,000  → disk, not the key zone, is the binding limit
```

Nginx の[サイズパーサー](https://github.com/nginx/nginx/blob/master/src/core/ngx_parse.c)は 2 進の乗数を使うため、`g` は GiB を意味します。一方、上のメディアサイズは 10 進です。つまり、この 50 GiB のエッジには、1 画質のカタログが約 3.58 個分入ります。ファイルごとのキャッシュヘッダーとファイルシステムのブロックオーバーヘッドを差し引く前です。もっと少なめに見積もり、`max_size` とディスク容量の下に運用上の余裕を残してください。適応ビットレートは使用量をさらに増やします。画質ごとに別のキー群になるため、同じ 5.6 時間を 3 画質でそろえると、すべて見られるなら 45 GB が要ります。フィルの帯域も反対側の話です。15 GB を 1 つのエッジへ 6 時間のオフピークウィンドウでプッシュするには、15 × 8 = 120 Gbit ÷ 21,600 s ≈ 5.6 Mbit/s の持続が必要です。1,000 個のエッジを 1 つのシールドから埋めれば、シールドを出るのは 6 時間にわたり約 5.6 Gbit/s です。

監視するもの: `max_size` に対するディスク使用量(上限に張り付いていると、マネージャーが絶えず追い出しています)、かつて `HIT` だったオブジェクトの `MISS` 率(追い出し後の再フィル。キャッシュがワーキングセットより小さいことのサインです)、リクエストヒット率ではなくバイトヒット率、ローンチ時のキーごとの上流リクエスト数です。どれもアクセスログに `$upstream_cache_status`、`$request_uri`、`$body_bytes_sent` を記録すれば取れます。

## 障害モードとエッジケース
- **リリース後のコールドスタート。** 純粋なプルCDNでは、新しいタイトルはローンチ時にどこでもヒットが 0 です。各エッジでの最初の視聴者が全員一緒にミスします。ローンチ直後のオリジンリクエストの急増として検知します。事前配置、ウォームアップ、シールド、合流で直します。
- **期限切れでのキャッシュスタンピード。** 人気のオブジェクトがどこでも同時に期限切れになり、次のバーストが全員ミスします。合流、`stale-while-revalidate`、不変のバージョン付き URL、TTLへのランダムなジッターを使います。
- **キャッシュキーの間違い。** ユーザーごとのクエリパラメーターがキーに入ると、すべてのリクエストが別物になり、ヒット率は崩れます。応答を変えるものをキーから落とすと、間違った版を出します。署名付き URL のクエリ文字列を落とすと、チェックなしで保護されたコンテンツを出すことがあります。キーと `Vary` ヘッダーを明示的に見直し、キャッシュの検索の前に認可してください。
- **個人データのキャッシュ。** `private` のないレスポンスは共有キャッシュに保存され、他のユーザーに出されることがあります。認証されたレスポンスには `private` または `no-store` を付け、テストしてください。
- **追い出しの繰り返し。** エッジがワーキングセットより小さければ、人気のオブジェクト同士が負荷の下で互いを押し出します。追い出し率とバイトヒット率を見てください。
- **視聴者と競合するフィルトラフィック。** プッシュは視聴者と同じ回線を使います。だから Open Connect 概要にあるようなオフピークのフィルウィンドウが大事です。
- **オリジンの停止。** TTLの短いプルCDNは、オリジンが死ぬとすぐに壊れます。ミスを埋められないからです。`stale-if-error` と、不変オブジェクトへの長い TTL がサービスを保ちます。[回線が切れたときに何を返すかの CAP の記事](https://systemdesignsimple.com/cable-to-asia-breaks/)と同じ可用性の考え方です。

## トレードオフ
| 選択肢 | 向いている用途 | 払うコスト | 使う場面 |
| --- | --- | --- | --- |
| オリジンだけ | シンプルさ、コピー 1 つ、即座の更新 | 遠くの視聴者には長い往復、すべての負荷がオリジンへ | オリジンに近い小さな視聴者層、プライベートまたはキャッシュできないデータ |
| プルCDN | 計画不要、キャッシュが実際の需要を追う、長い裾が安い | オブジェクトごとエッジごとの最初のリクエストがミスを全額払う、リリース時のバースト | 需要が予測できない大きなカタログ、ウェブサイト、キャッシュできるレスポンスの API |
| プッシュCDN | 最初の視聴者が速い、フィルに空き時間を使える | 各エッジのストレージ、配置システム、予想が外れれば無駄なコピー | 人気が予測できるコンテンツ、大きなローンチ、需要が分かっている動画カタログ |
| ハイブリッド: 先頭をプッシュ、裾をプル | 大事なものは最初の視聴から速い、ストレージは抑えられる | 人気の予測と 2 つのコードパス |
| オリジンシールド(階層キャッシュ) | 理想的にはキーごとシールドごと滞在期間あたり 1 回の成功したフィル(合流あり)、長い区間のミスが減る | フルミスで 1 ホップ増える、もう 1 層の運用 |
| バージョン付き URL と長い TTL | 更新による無効化を避けられる、パージ不要。ヒット率は滞在、需要、容量に依存します | ファイルをリネームするビルド手順 |

## よくある間違い
**間違い:** 「CDNはすべてのリクエストを速くする」と言うこと。 **代わりに:** プルCDNが速くするのは繰り返しのリクエストです。オブジェクトごとエッジごとの最初のリクエストはミスで、オリジンだけよりわずかに遅くなることがあります(私たちのモデルでは 318 ms に対して 335 ms)。

**間違い:** プッシュとプルを二者択一として扱うこと。 **代わりに:** 予測できる先頭部分をプッシュし、裾をプルし、次のセグメントを先読みし、シールドを加えます。どのコンテンツをどこへ置くか、その理由を説明してください。

**間違い:** 平均ヒット率だけを引用すること。 **代わりに:** 計算を示してください。TTFB の期待値は加重平均で、1 段モデルのオリジン負荷はミス率 × リクエスト数で、ミスのコストはヒット率の上のパーセンタイルに出ます(ヒット率がちょうど 99% なら、p99.9 が示し、p99 は示さないことがあります)。

**間違い:** 変更を公開するためにファイルをパージすること。 **代わりに:** URL にバージョンやハッシュを入れ、オブジェクトを不変とマークすれば、キャッシュに何も伝える必要はありません。

**間違い:** 帯域とレイテンシを混同すること。 **代わりに:** 遠くのオリジンへのパイプを太くしても往復は短くなりません。バイトを近くへ移すだけです。私たちのモデルでは、どの経路でも転送時間を同じにしても差は残りました。

**間違い:** リリース時にオリジンを忘れること。 **代わりに:** 同時ミスのバーストに備えてください。キャッシュを温め、リクエストの合流を有効にし、オリジンの前にシールドを置き、オリジンのリクエスト率をローンチの主要な指標として監視します。

## 面接で聞かれたら
1. **確認する:** 動画か小さなファイルか。オンデマンドかライブか。リージョンはいくつか、カタログはどれくらい大きいか、人気はどれくらい偏っているか。
2. **仮定を述べる:** オリジンとエッジまでの往復時間、セグメントのサイズと長さを言い、それらが仮定だと伝えます。
3. **構成:** プレイヤーとマニフェスト、エッジへのルーティング、エッジキャッシュ、任意のシールド、オリジン。プルの経路の横にプッシュのフィル経路を置きます。
4. **深掘り:** ミスのコスト、ヒット率の計算、キャッシュキーと `Cache-Control`、合流、何をいつプッシュするか。
5. **トレードオフ:** ストレージと最初の視聴のレイテンシ、鮮度とヒット率、シールドのホップとオリジンの保護。
6. **締めくくり:** ほとんどのリクエストは近くのヒットです。設計の仕事は、大事なコンテンツの最初のリクエストもヒットにすることです。ストレージを無駄にせずに。

**60 秒で答える**

距離がレイテンシの下限を決めるため、オリジンから遠い視聴者は動画のセグメントごとに長い往復を払います。CDNは視聴者の近くにエッジキャッシュを置きます。プレイヤーはマニフェストを取り寄せ、次に各セグメントを普通の HTTP オブジェクトとして取り寄せるため、エッジはローカルのコピーから出せます。プルCDNでは、エッジは最初のミスで取り寄せてコピーを保持するため、各オブジェクトの各エッジでの最初の視聴者は今もオリジンまでの往復とミス処理を払います。私たちが遅延を選んだ小さな決定的モデルでは、最初のセグメント全体を待つ前提で、起動時間のモデル値は 335 ms で、オリジンだけの 318 ms より遅く、2 番目の視聴者は 75 ms でした。プッシュCDNでは、コンテンツは再生前に置かれるため、最初の視聴者も 75 ms です。Netflix の Open Connect 概要によると、彼らはコンテンツを事前に置き、多くはオフピークに行います。先頭部分が予測できるなら、ハイブリッドでそれをプッシュし、長い裾はプルします。オリジンシールドとリクエストの合流がオリジンへのフィルを減らし、バージョン付きセグメント URL への長い TTL がパージを避けます。私なら、バイトヒット率、キーごとのオリジンリクエスト率、追い出しによる再フィル、起動時間をマニフェスト、ライセンス、最初のセグメントに分けた値を監視します。

## 練習問題

**[初級] プルCDNとプッシュCDNの違いは何ですか?**

プルエッジは、初めてミスしたリクエストでオリジンからオブジェクトを取り寄せて保持します。プッシュエッジは、誰かが頼む前にオブジェクトがコピーされているため、最初のリクエストからヒットになります。

**[初級] なぜHTTPキャッシュは動画を配信できるのですか?**

HLS や DASH のようなストリーミング形式は、動画をマニフェストに並んだ短いセグメントに切り、各セグメントを普通の HTTP GET で取り寄せます。セグメントはただのキャッシュできるオブジェクトで、URL が付いています。

**[中級] エッジが 10 ms 先、オリジンがその先 240 ms、ミス処理が 15 ms、サーバーが 1 台あたり 5 ms のとき、ミスとヒットの TTFB はいくらですか?**

ミス: 10 + 15 + 240 + 5 + 5 = 275 ms。ヒット: 10 + 5 = 15 ms。私たちのモデルでは、全チャンクの平均値は 273 ms と 15 ms でした。

**[中級] ヒットが 15 ms、ミスが 273 ms のとき、ヒット率 90% と 99% での TTFB の期待値はいくらで、オリジン負荷はどう変わりますか?**

90% では 13.5 + 27.3 = 40.8 ms。99% では 14.85 + 2.73 = 17.58 ms。オリジンへのリクエストは、エッジへのリクエストの 10% から 1% へ落ち、10 分の 1 になります。

**[中級] なぜ私たちのモデルでは、最初のプル視聴者がオリジンだけより遅かったのですか?**

ミスはオリジンへの経路のすべてに加えて、エッジへのホップ、15 ms のミス処理、もう 1 回のサーバー遅延を払います。だから起動時間のモデル値は 335 ms で 318 ms より遅く、300 ms のリードではそれ以降のすべてのチャンクが止まりました(16 回に対して 19 回)。

**[上級] 新しいエピソードのローンチで、オリジンのトラフィックが 10 分間 10 倍に跳ねました。何が起きて、何を変えますか?**

すべてのエッジが新しいセグメントを一度にミスしました(コールドスタート。スタンピードの可能性もあります)。リリースをオフピークのフィルウィンドウでエッジへ事前に配置し、キャッシュを温め、エッジとシールドでリクエストの合流を有効にし、オリジンの前にシールドを置いて、理想的にはキーごとシールドごと滞在期間あたり 1 回の成功したフィルにします。フィルがロックのタイムアウト(上の設定では 5 秒)以内に終わることを確認してください。終わらなければ、待っているリクエストが上流へ行き、急増は続きます。

**[上級] デプロイのあと、トラフィックが変わっていないのにエッジのヒット率が 95% から 40% へ落ちました。どこを見ますか?**

キャッシュキーとレスポンスヘッダーです。新しいクエリパラメーターや `Vary` に加わったヘッダーが、すべてのリクエストを別物にすることがあります。間違って加わった `Cache-Control: private` や `no-store` はキャッシュを完全に止めます。`$upstream_cache_status` の分布、キャッシュキー、`Cache-Control` を前後で比べ、どのキーが `HIT` から `MISS` へ変わったかアクセスログで確認してください。

**[上級] 修正した動画セグメントを、何千ものエッジをパージせずに公開するにはどうしますか?**

新しい URL(パスにバージョンやコンテンツハッシュ)でエンコードし、それを指す新しいマニフェストを公開します。古いセグメントは有効なまま不変です。短い TTL や自分自身のバージョンが必要なのはマニフェストだけです。

## チートシート
| 用語または式 | 意味 |
| --- | --- |
| オリジン | 正本。すべてのキャッシュはここから埋めます |
| エッジサーバー | 視聴者の近くのキャッシュ。ヒットにはローカルで答えます |
| プル | 最初のミスで取り寄せ、次の視聴者のために保持します |
| プッシュ(事前配置、ウォーミング) | 誰かが頼む前にコピーしておきます |
| ミスの TTFB | エッジへのホップ + ミス処理 + オリジンへのホップ + サーバー処理 |
| ヒットの TTFB | エッジへのホップ + エッジのサーバー処理 |
| E[TTFB] = h × ヒット + (1 − h) × ミス | ヒット率 h での平均レイテンシ |
| オリジン負荷 ≈ (1 − h) × リクエスト数 | 1 段、合流なし、再検証なし、ウォームアップなし、シールドなし |
| バッファが 0 になると停止 | バッファされた秒数と持続的な配信速度で決まります。私たちのラボでは TTFB + 転送時間 > リード時間と単純化しています |
| セグメントサイズ = ビットレート × 時間 ÷ 8 | 6 Mbit/s × 2 s ÷ 8 = 1.5 MB。10,000 セグメント = 15 GB |
| Nginx の inactive と鮮度 | アクセスのないエントリは、新鮮でも inactive を過ぎれば削除されます |
| Cache-Control: s-maxage / max-age | 共有キャッシュ / すべてのキャッシュの鮮度(RFC 9111) |
| Age | オリジンでの生成または検証からの秒数。Age: 0 でもヒットの場合があります |
| キャッシュキー | デフォルトではクエリ文字列を残します。キャッシュの検索の前に認可します |
| stale-while-revalidate | 今は古いものを出し、裏で更新します |
| オリジンシールド | 中間のキャッシュ層。理想的にはキーごとシールドごと滞在期間あたり 1 回の成功したフィル |
| リクエストの合流 | 同時のミスは 1 回のフィルを待ちます(proxy_cache_lock)。5 秒のロックタイムアウトを過ぎた待機者は上流へ行きます |
| 私たちのモデル(起動時間のモデル値) | オリジン 318 ms、プル視聴者 1 は 335 ms、プル視聴者 2 は 75 ms、プッシュ視聴者 1 は 75 ms |
