オンデバイスAIがネットワークなしで答えられるのは、モデルが自分のマシンで動くからです。重み、トークナイザー、設定はディスク上のファイルで、llama.cppのようなランタイムがローカルのチップで計算します。ネットワークなしでできないのは、ライブの情報に届くことです。最新の情報は、渡された文書かツールから来なければなりません。


## 定義
**ローカル推論**: モデルをユーザーのデバイス上で実行すること。プロンプトがデバイス内に留まるかどうかは、アプリのネットワークとストレージの動きにもよります。

**重み**: モデルの学習済みの数値で、サイズのほぼすべてを占めます。

**量子化**: 各重みを少ないビット数(16ではなく4〜5程度)で保存することで、モデルをずっと小さくします。

## ネットワークなしで、オンデバイスAIはどう答えるのか
典型的なテキストモデルでは、GGUFが重み、トークナイザーのデータ、アーキテクチャのメタデータを1つのファイルにまとめられます。重みがバイト数のほぼすべてです。トークナイザーはテキストをトークンIDに変え、また戻します。メタデータは層の数、アテンションヘッド、コンテキスト長を与えます。llama.cppが使う[GGUF仕様](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)は、モデルを読み込むのに必要な情報を「すべて含む」ことを目指すと書いていて、大きなモデルをシャードに分割することもできます。

![GitHub上の公式GGUF仕様ページのスクリーンショット](https://systemdesignsimple.com/img/posts/how-can-ai-answer-with-no-network/source-1.webp)

ランタイムはそのファイルを読み込み、プロンプトをトークン化して、CPUやGPUで層を実行します。どの手順もリモートサーバーは要りません。ローカルアプリは、モデルに渡す前に文書の該当箇所を選ぶ[RAG検索](https://systemdesignsimple.com/how-ai-finds-one-line-in-100-pages/)も使えます。

サイズの最初の見積もりは、重みだけを数えます。

```text
weight GB = parameters × average bits per weight / 8 / 1e9
small: 1.5e9 × 4.85 / 8 / 1e9 = 0.909375 GB ≈ 0.91 GB
8B:    8e9 × 4.85 / 8 / 1e9 = 4.85 GB
```

実際のGGUFファイルは、トークナイザー、メタデータ、アライメントの分だけ少し大きくなります。

## ノートパソコンはどれくらい速く答えを書けるか
2つの段階があります。プリフィルはプロンプトのトークンを並列に、たいていチャンク単位で処理します。次にデコードがトークンを1つずつ書き出すため、[返信は1語ずつ流れてきます](https://systemdesignsimple.com/why-ai-starts-answering-before-done/)。重みがプロセッサーのキャッシュより大きい場合、1つの系列を生成する密なモデルのデコードは、メモリ帯域幅で決まることがよくあります。新しいトークンごとに、重みをチップへ流し込まなければならないからです。大まかな見積もりは、実効帯域幅を重みのバイト数で割ったものです。アテンションキャッシュの転送とランタイムのオーバーヘッドは入っていません。

下の計算は、その条件を仮定しています。密なモデル、バッチサイズ1、重みはRAMの中です。

```text
tokens/s ≈ bandwidth x efficiency / weight bytes
small: 120 GB/s x 0.65 / 0.91 GB ≈ 86 tokens/s ≈ 64 words/s  (0.75 words per token)
8B:    120 GB/s x 0.65 / 4.85 GB ≈ 16 tokens/s ≈ 12 words/s
```

シミュレーションは、シード付きのタイミング変動を入れて、想定した単語数を丸め、プロンプトごとの速度を平均したあと、65.4と12.2 words/sを出します。これらの速度は仮定の値です。実際のモデルで測ったものではまだありません。この条件の外では、比率は変わります。バッチ処理は重みの1回の読み取りを多くの系列で共有し、Mixture-of-Expertsのモデルはトークンごとに重みの一部だけを読み、長いコンテキストはキャッシュの読み取りを増やします。5倍小さいモデルが5倍速いとは限りません。[llama.cppの性能のヒント](https://github.com/ggml-org/llama.cpp/blob/master/docs/development/token_generation_performance_tips.md)でも、GPUへのオフロードとスレッド設定が大きく効くと示されています。

## メモリはどれくらい要るか
メモリは、アテンション(KV)キャッシュも保持しなければなりません。すべてのトークンについてキーと値を、[コンテキストウィンドウ](https://systemdesignsimple.com/my-chat-forgot-my-name/)の中に保存します。ここで`kv_heads`はキー/値ヘッドの数、`head_dim`は各ヘッドのサイズで、式は2バイトの要素と1つの系列を仮定しています。

```text
KV cache = layers x 2 (K and V) x kv_heads x head_dim x 2 bytes x context
small: 28 x 2 x 2 x 128 x 2 x 4096 = 0.12 GB  -> subtotal 0.91 + 0.12 + 0.3  = 1.33 GB
8B:    32 x 2 x 8 x 128 x 2 x 4096 = 0.54 GB  -> subtotal 4.85 + 0.54 + 0.55 = 5.94 GB
```

最後の項は想定した作業用バッファなので、これらはモデル、キャッシュ、バッファの見積もりの小計です。どちらも16 GBを下回ります。実際のメモリ使用量は計測が必要です。理想化したディスク転送時間は、重みのバイト数をディスク速度で割ったもので、想定した3 GB/sでは0.3秒と1.62秒です。これがモデルが使えるようになるまでの全時間ではありません。

## 私たちのラボが示すこと、示さないこと
ai-16のラボは、Nodeのネットワーク関数7つにパッチを当て、呼び出しがあればソケットが開く前に例外を投げるようにし、7つすべてが投げることを確認してから、テスト用のクラウドクライアントに20個のプロンプトを送ります。クラウドクライアントは20件中0件の返信でした。ネットワークを切ることが、リモートモデルに頼るアプリに何をするか、1つのプロセスの中で示しています。

![私たちのai-16ラボ実行のターミナル出力: node run.mjs](https://systemdesignsimple.com/img/posts/how-can-ai-answer-with-no-network/lab-run.webp)

同じスクリプトは2つの「ローカルモデル」の結果も出しますが、あらかじめ決めた文字列であって推論ではないので、ここでは省きます。ラボがテストするのはJavaScriptのインターセプターで、オフラインAIそのものについてはほとんど何も言えません。本当のテストは、GGUFモデルをllama.cppで動かし、OSで外向きの通信を遮断して、モデル、量子化、ランタイムのバージョン、コマンド、出力、そして接続の試行がゼロであることを示す接続モニターを記録することです。そのテストはまだ実行していません。

インターセプターの核はこうです。

```js
// block.mjs: make network calls fail before a socket exists (Node 22)
import net from 'node:net';
const log = [];
function block(kind, target) {
  log.push({ kind, target });
  const err = new Error(`blocked ${kind} -> ${target}`);
  err.code = 'ENETUNREACH';
  throw err;
}
globalThis.fetch = async (url) => block('fetch', String(url));
net.connect = net.createConnection = (opts) => block('net.connect', `${opts.host}:${opts.port}`);

try { await fetch('https://probe.invalid/'); } catch (e) { console.log(e.code); } // ENETUNREACH
console.log(log.length, 'call(s) blocked');
```

## オフラインのモデルは何を知ることができないか
オフラインのモデルは、新しい外部の出来事を自分で観測することはできません。学習したパターンと与えられた情報から推論はできますが、今朝の見出しを確認するには、渡された文書や[アプリがつなぐツール](https://systemdesignsimple.com/how-ai-learns-new-apps-tool-discovery/)のような、最新の情報源が必要です。

日付も同じです。アプリはデバイスの時計を読めます。ネットワークは要りません。その日付をプロンプトに入れるのです。日付を自分で入力することも、含んだローカルファイルを開くこともできます。

## トレードオフ
下の速度とRAMの数値は、上の見積もりで、想定した構成だけのものです。

| 選択肢 | 良いところ | 代償 | 使う場面 |
| --- | --- | --- | --- |
| 小さいローカルモデル(重み約0.9 GB) | RAMが少ない(見積もり約1.3 GB)、リモートの推論サービスなしで動く | パラメーターが少ない | 控えめなハードウェアでの短いタスク |
| 中くらいのローカルモデル(重み約4.9 GB) | パラメーターが多い、リモートの推論サービスなしで動く | デコードの見積もりが遅い、RAMの見積もり約5.9 GB | RAMに余裕のあるマシン |
| クラウドモデル | デバイスのメモリ容量を超えるモデルを動かせる | ネットワークが必要、プロンプトがリモートサービスへ行く | ローカルのメモリや計算が足りないとき |

## 私たちの見解
サイズとメモリの式は、モデルをダウンロードする前の最初の確認として筋が通っています。パラメーター数×重みあたりのビット数が重みのバイト数で、KVキャッシュとバッファがその上に来ます。速度の式はもっと荒いものです。RAMの中の重みを使い、1つの系列を密にデコードする場合にだけ成り立ち、キャッシュの転送とランタイムのオーバーヘッドを無視しています。実際のモデルで速度も答えの質もまだ測っていないので、86と16 tokens/sは、想定した1台のノートパソコンでの見積もりとして扱ってください。OSレベルで通信を遮断する実行が済むまでは。
