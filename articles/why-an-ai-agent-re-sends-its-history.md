AIエージェントのトークンが積み上がるのは、構造的な理由があります。追加だけのエージェントループでは、モデルを呼び出すたびに、それまでの会話が論理的なコンテキストとして入ります。クライアントが送り直すか、サービスが保存した会話の状態から組み立てるかは違いますが、どちらにしても、呼び出しkの入力はそれまでのすべてです。増分がほぼ一定なら、N回の入力の合計はN²に近づき、そのほとんどは古いツール出力を数え直したものです。面接で聞かれる形にすると、「コーディングエージェントの入力トークンがチャットの5,000倍です。トークンはどこへ行き、請求をどう下げますか」です。


## 前提
**モデルは呼び出しのあいだ何も覚えていません。** 1回の呼び出しは、システムプロンプト、ツール定義、そのときのメッセージでできたコンテキストだけで計算します。複数ターンの会話が成り立つのは、クライアントが前のターンをもう一度送るか、サービスが保存した会話の状態から組み立てるからです。

**ツール呼び出し。** モデルはファイルを読んだりテストを実行したりできません。ツールの名前と引数を書いた構造化リクエストを出し、アプリがツールを実行し、その結果が新しいメッセージとしてモデルへ戻ります。エージェントは、このループを、モデルがツール呼び出しではなく最終回答を返すまで繰り返したものです。

**トークンと価格。** APIは入力トークン(送るもの)と出力トークン(モデルが書くもの)を、100万トークンあたりの別々の価格で課金します。出力のほうがたいてい高くなります。数は各モデルのトークナイザーで決まるので、それ以外の数は見積もりです。

## 用語の定義
**エージェントループ**: モデルを呼び、モデルが求めたツールを実行し、そのリクエストと結果をメッセージ一覧へ追加し、モデルが最終回答を返すまでもう一度モデルを呼ぶ、クライアント側のループ。

**固定部分(F)**: タスクのすべての呼び出しで同じように送られる内容。システムプロンプト、ツールのスキーマ、タスクの文章、それに直列化の枠組み。ラボではリクエスト1で、2,230トークンの見積もりです。

**増分(a_k)**: 呼び出しkが履歴に加えるトークン。そのモデルのメッセージとツール結果です。リクエストk+1に初めて現れ、その後のすべてのリクエストに入ります。

**再送の割合**: タスクの入力トークン全体のうち、同じタスクのそれまでのリクエストですでに送ったものの割合。

**読んだ倍率、合計の倍率、コストの倍率**: エージェントの入力をチャットの入力で割ったもの。エージェントの入出力の合計をチャットの入出力の合計で割ったもの。エージェントのコストをチャットのコストで割ったもの。それぞれ別の問いに答えます。

**プロンプトキャッシュ**: リクエストの先頭部分について計算したキーと値のテンソルを保存し、あとで同じ先頭で始まるリクエストが来たときに再利用する、プロバイダーの機能です。再利用されたトークンはキャッシュ読み取りの価格で課金されます。モデルは全文を入力として受け取ります。

**圧縮とコンテキスト編集**: すでに保存された履歴の一部を消したり、空にしたり、要約したりして、あとのリクエストが運ぶ量を減らすこと。新しいツール結果を履歴に入る前に小さくすることとは別の手法です。

## エージェントはどうやって履歴を送り直すのか
この記事の裏にあるラボ([`labs/ai-7`](https://github.com/systemdesignsimple/labs/tree/main/labs/ai-7))は、おもちゃのコーディングエージェントを作ります。合成シミュレーションで、トークンは見積もりです。課金された実行ではなく、どの製品の実際の数字でもありません。すべてのリクエストは、`system`、`tools`、`messages`を持つ1つのJSONとして直列化され、枠組みも含めて全体で数えられます。この記事のすべての数は、JSONのキーや引用符、エスケープも含めた合成JSONサイズのトークン見積もりです。実際のAPIはHTTPボディをトークン化しません。メッセージとツール定義を、モデルごとの入力形式に変換し、その形式独自の制御トークンを付けます。だから、リクエストJSONを実際のトークナイザーで数えても、課金される使用量にはなりません。本番の会計では、呼び出し前にプロバイダーのトークン数え上げエンドポイントを使い、呼び出し後に返ってくる`usage`オブジェクトを見てください。見積もりは比率と形を見るには十分で、ラボが主張するのはそこです。

```text
request 1   [system][10 tool schemas][task]
request 2   [system][10 tool schemas][task][msg 1][result 1]
request 3   [system][10 tool schemas][task][msg 1][result 1][msg 2][result 2]
...
request k   [固定部分 F][呼び出し 1 から k-1 までのすべて]
```

呼び出し1からN-1までは、それぞれ短いメッセージと1つのツール呼び出し(`read_file`、`grep`、`run_tests`、`edit_file`、`list_dir`)を書き、ツール結果が履歴に加わります。呼び出しNが最終回答を書きます。何も消しません。ループは追加だけです。これが、このあとすべてが成り立つ条件です。

![1つのチャット吹き出しが158トークンと書かれた薄い紙を持ち、その横に1つのコーディングタスクの高い紙の塔があり、入力5,467倍の判が押されている](https://systemdesignsimple.com/img/why-an-ai-agent-re-sends-its-history/b01.webp)

1回のチャットは入力158トークンの見積もりです。ラボの30回のエージェントタスクは、その5,467倍を送ります。

履歴を誰が持つかは、モデルが何を計算するかとは別の話です。[OpenAIの会話状態ガイド](https://developers.openai.com/api/docs/guides/conversation-state)には両方の方式があります。自分で前のメッセージをもう一度渡すか、保存された応答へ`previous_response_id`でつなぐかです。後者の場合も、ガイドによれば、チェーンにあるそれまでの入力トークンはすべて入力として課金されます。サーバー側の状態はアップロードのバイト数を減らしますが、論理的なコンテキストは小さくなりません。

毎回の呼び出しで論理的なコンテキストが必要な理由は、トランスフォーマーがリクエストを処理する2つの段階にあります。

- **プリフィル。** すべての入力トークンが、すべての層を並列に通ります。各層はすべてのトークンをキーと値のベクトルに変換し、各トークンはそれまでのすべてのトークンに注意を向けます。結果が**KVキャッシュ**です。層ごとに、トークン1つあたり1行のキーと値のテンソルがあります。コストは、入力の長さLに比例する部分(射影とMLP、パラメータ1つあたりトークン1つで約2 FLOP)と、トークンのすべてのペアのスコアを計算する二次の注意の部分(因果マスク付きで約2·層数·L²·d_model FLOP)に分かれます。
- **デコード。** 出力トークンを1つずつ生成します。新しいトークンは自分のクエリ、キー、値を計算し、保存されたKVキャッシュに注意を向け、1行を追加します。出力トークン1つあたりのデコードコストはLに比例し、たいていはメモリ帯域が律速になります。生成されるトークンごとにKVキャッシュ全体を読むからです。

KVキャッシュはリクエストごとです。リクエストが終わるとサーバーは解放します(プロンプトキャッシュの下では一部を残すこともあります)。だから、呼び出し20は、同じ先頭部分がまだキャッシュされていない限り、呼び出し4で計算したものを何も使えません。公開されているオープンウェイトの形を例にした、80億パラメータ級のオープンモデルの数字です(32層、KVヘッド8個、ヘッド次元128、16ビット値、約80億パラメータ、d_model 4,096)。どのプロバイダーの提供モデルでもありません。

```text
トークンあたりのKVバイト数 = 2(KとV) × 32層 × 8ヘッド × 128次元 × 2バイト = 131,072 B = 128 KiB
リクエスト30(51,686トークン) = 51,686 × 131,072 B = 6,774,587,392 B ≈ 6.31 GiBのKV状態

プリフィルのFLOP、線形部分    ≈ 2 × 8e9 × L
プリフィルのFLOP、注意の部分 ≈ 2 × 32 × L² × 4,096
注意 / 線形            ≈ 32 × 4,096 × L / 8e9 = L / 61,035
L = 51,686のとき       ≈ 0.85、つまり注意はすでにプリフィルの半分近く
```

つまり「モデルはすべてのトークンを読む」には、3つの違うコストが隠れています。アップロードのバイト数(サーバーが履歴を持つならゼロ)、プリフィルの計算(キャッシュされていないLに対して超線形)、KVメモリとデコードの帯域(Lに比例)です。先頭部分のキャッシュは、キャッシュされた部分のプリフィルをなくします。新しい末尾だけが射影され、新しいトークンはそれぞれ全文のコンテキストに注意を向けます。オープンソースのサーバーが中でどう動くかは、[vLLMの自動プリフィックスキャッシュ](https://docs.vllm.ai/en/latest/design/prefix_caching.html)が示しています。KVキャッシュを固定サイズのブロックに分け、各ブロックをトークンのハッシュと1つ前のブロックのハッシュで鍵付けし(ブロックが一致するのは先頭全体が一致するときだけ)、参照されなくなったブロックをLRU順に追い出します。ハッシュがつながっているので、プロンプトの早い場所で1バイト変わると、それ以降はすべて無効になります。

ラボの中くらいの設定を、リクエストごとに並べます(全体の大きさ / その中の新しいトークン)。

```text
[1]  2,230 / 2,230    [10] 17,747 / 1,261    [20] 39,949 / 2,003    [30] 51,686 / 1,375
[2]  3,123 /   893    [11] 18,894 / 1,147    [21] 40,455 /   506
[3]  6,190 / 3,067    [12] 19,304 /   410    [22] 44,603 / 4,148
```

![呼び出し1から30までの30本の棒グラフ。各棒は送り直したトークンの灰色に、新しいトークンの細いオレンジ色または黄色の頭が乗り、コピー機の下にある](https://systemdesignsimple.com/img/why-an-ai-agent-re-sends-its-history/b03.webp)

1つのタスクの30回のリクエスト。灰色が送り直した履歴で、細い頭が新しい部分です。

新しい部分は小さく、ツールによってばらつきます(リクエスト2から30では319から4,942トークン)。全体の大きさは上がる一方です。リクエスト30は51,686トークンで、そのうち新しいのは1,375だけです。呼び出し29のツール結果とメッセージ、それに枠組みです。残りの50,311トークンは、リクエスト29とちょうど同じ大きさで、コピーです。

## なぜトークンはN²に近づくのか
R_kをリクエストkの大きさとします。固定部分F、増分a_1からa_N-1、何も消さないとすると、こうなります。

```text
R_k  = F + a_1 + a_2 + ... + a_(k-1)

正確な式(増分が何でも):
T(N) = R_1 + R_2 + ... + R_N
     = N·F + j=1からN-1までの a_j · (N - j) の合計   (ステップjは、その後のN - j回のリクエストで送り直される)

増分が一定の近似(a_j = a がすべて同じ):
T(N) = N·F + a·N(N - 1)/2                         (等差数列)
S(N) = 1 - [F + (N - 1)·a] / T(N)                 (再送の割合)
```

正確な合計は重み付きの和です。増分jの重みはN - jです。a_jのふつうの平均を近似式に入れると、増分が均等に散らばっているときにだけ正確になります。タスクの早い段階の大きな結果(重みが大きい)は実際の合計を近似より上に押し、遅い段階の大きな結果は下に押します。1番目の項はNに比例し、2番目は二乗です。短いタスクでは固定部分が支配的で、長いタスクでは履歴の項が支配的です。早いツール出力がいちばん高くつきます。30回のタスクの呼び出し2での大きなファイル読み取りは、その後の28回のリクエスト(リクエスト3から30)で送られます。

ここから2つの性質が出てきます。

**新しいトークンは telescoping(相殺)します。** リクエストkの新しいトークンはR_kからR_k-1を引いたものなので、タスク全体で合計するとR_N、つまり最後のリクエストの大きさになります。ラボの30回では、新しい入力の合計は51,686で、リクエスト30と同じです。合計の残りはすべて、前に送ったものです。

**再送の割合は、履歴の項が支配的なときに1 - 2/Nに近づきます。** 再送の割合は、正確には1 - R_N / T(N)です。増分が一定の近似では、(N-1)·aがFよりずっと大きくなると、R_Nは約aN、T(N)は約aN²/2になるので、Sは1 - 2/Nに近づきます。N = 30なら1 - 2/30 = 93.3%です。ラボで測った値はこうでした。

```text
再送の割合 = 1 - R_30 / T(30) = 1 - 51,686 / 863,762 = 1 - 0.0598 = 94.0%
```

この割合はN、F / aの比、増分がタスクのどこに散らばっているかで決まります。増分だけを大きくしてもSは変わります。Fは変わらないからです。増分が小さいと、固定部分が各リクエストに占める割合が大きくなります。ラボでは、呼び出し30までにFは履歴のそばでは小さくなっているので、下の3つの切り詰め設定の再送の割合は0.2ポイント以内に収まります(94.1%、94.0%、93.9%)。

![30回の呼び出しの階段全体に1つの括弧があり、合計30回の灰色の部分がまとめて色付けされ、94.0%再送のラベルが付いている](https://systemdesignsimple.com/img/why-an-ai-agent-re-sends-its-history/b05.webp)

30回の呼び出しの合計で、入力の94.0%は送り直した履歴でした。

**指数を測る。** T(N)がc·N^pのようにふるまうなら、T(50)/T(10) = 5^pなので、p = log(T(50)/T(10)) / log 5です。ラボの数字はこうです。

```text
T(10) =    98,386        T(50) = 2,358,122
T(50) / T(10) = 23.97                       (呼び出しが5倍)
p = log(23.97) / log(5) = 3.177 / 1.609 = 1.97
純粋な二乗なら5² = 25倍。線形のN·Fの項が25を下回らせる
```

文字数/4という粗い見積もりでは比率は21.31倍なので、結論は数え方にはよりません。指数は、10回から50回のあいだの局所的な当てはめであって法則ではありません。固定部分が、短いタスクでは指数を1のほうへ引きます。

システムの言葉で言えば、論理的な入力トークンは1回の呼び出しでは線形に増え、追加だけのタスク全体では二乗に近く増えます。アップロードのバイト数、推論の仕事、レイテンシは別々に考える必要があります。アップロードのバイト数は、クライアントが履歴を送る場合にだけトークンの曲線をたどります。サーバーが状態を持つなら、各増分の大きさに近くなります。キャッシュされていないプリフィルの仕事は、注意の部分がL²で増えるので、1回の呼び出しでも線形より速く増えます。先頭部分のキャッシュが温まっていれば、1回の呼び出しのプリフィルは、新しい末尾とコンテキスト長の積にほぼ比例します。KVメモリと出力トークン1つあたりのデコードコストはLで増えます。エージェントのステップ上限を2倍にすると、履歴の部分の論理的な入力はおよそ4倍になります。入力トークンのレート制限は、ステップ数よりも長いタスクのほうをずっと強く打ちます(プロバイダーがキャッシュ読み取りを制限に数えるかは、プロバイダーとモデルで違うので確かめてください)。

## 「何倍」が3つあるのはなぜか
基準は、ラボの1回のふつうのチャットです。入力158トークン(システムプロンプトと1つの質問、同じJSONの枠組み)、出力601トークン、例示のコストで0.0095ドルです。中くらいの設定の30回のタスクと比べると、こうなります。

```text
読んだ倍率      = エージェントの入力 / チャットの入力
                = 863,762 / 158                                   = 5,467倍
合計の倍率      = (エージェントの入+出) / (チャットの入+出)        = 1,141倍
コストの倍率    = エージェントのコスト / チャットのコスト = 2.6271ドル / 0.0095ドル = 277倍   (チャットのコストは丸める前で0.009489ドル)
```

3つが違うのは、2つの仕事の形が正反対だからです。価格は例示で、入力100万トークンあたり3ドル、出力100万トークンあたり15ドルです。よくある公開価格表の形であって、どの製品の見積もりでもありません。出力は入力の5倍の単価です。

```text
1回のチャット:   入力  158 × 3 / 100万  = 0.000474ドル
                 出力 601 × 15 / 100万 = 0.009015ドル      出力 = チャットのコストの95.0%
エージェント、30回:  入力  863,762 × 3 / 100万 = 2.5913ドル     入力  = エージェントのコストの98.6%
                 出力 = 2.6271ドル - 2.5913ドル = 0.0358ドル  → 約0.0358 / 15 × 100万 ≈ 2,388出力トークン
確認:      (863,762 + 2,388) / (158 + 601) = 866,150 / 759 = 1,141倍
```

チャットはほとんどが高価な出力で、エージェントはほとんどが安い入力です。入力を入力で割る(5,467倍)と、チャットがいちばん小さい部分で比べます。コストをコストで割る(277倍)と、払うものを比べます。どちらも間違いではありませんが、「1つのタスクはチャット1,000回分のコスト」というのはコストの主張です。このラボでは、中くらいの設定は50回でも届きません(752倍)。重い設定の50回だけが超えます(1,411倍)。どの倍率かをいつも言ってください。

## 古いツール結果を切り詰めると何が変わるか
答えは、切り詰めがいつ起きるかで変わります。

**履歴に入るときにツール結果を小さくする(シミュレーション済み)。** ラボは、同じステップと内容で3つの合成設定を動かします。それぞれツール出力の決まった割合だけを残すので、軽い設定は重い設定の正確な先頭部分で、大きさだけが違います。

| 30回 | 残す割合 | 入力の合計 | 最後のリクエスト | 再送 | コスト(キャッシュなし) | コスト(キャッシュあり) | チャットの何倍 |
|---|---|---|---|---|---|---|---|
| 軽い | 20% | 417,788 | 24,801 | 94.1% | 1.29ドル | 0.2467ドル | 136倍 |
| 中くらい | 50% | 863,762 | 51,686 | 94.0% | 2.63ドル | 0.4733ドル | 277倍 |
| 重い | 100% | 1,581,678 | 96,275 | 93.9% | 4.78ドル | 0.8425ドル | 504倍 |

式T(N) = N·F + a·N(N-1)/2で読んでください。入るときに切り詰めると、履歴の項の傾きaが下がります。Fも、モデルの自分のメッセージも、Nも触りません。だから、こうなります。

- **入力の合計は、残す割合には比例しません。** 軽い設定はツール出力の20%だけを残しますが、重い設定の入力の417,788 / 1,581,678 = 26.4%を送ります。固定部分とモデルのメッセージは切り詰められないからです。
- **再送の割合はほとんど動きません**(94.1%、94.0%、93.9%)。30回では、3つの設定すべてで履歴の項がFをはるかに上回るからです。Fがもっと大きいか、タスクがもっと短ければ、同じ切り詰めでもSはもっと動きます。曲線は形を保ったまま、小さくなります。50回では、軽い設定でもまだ1,115,728トークンで、96.0%が再送です。
- **コストの倍率は大きく変わります**。30回では136倍から504倍です。エージェントのコストのほとんどが入力だからです。

実務ではこうします。`grep`は一致数の上限を付け、ファイル読み取りは行の範囲を指定し、テスト出力は失敗だけにし、一覧はページを分けます。呼び出しjで加えたトークンは、その後のN - j回も払うので、ツール出力の上限は、長いタスクの早い段階でいちばん効きます。

**すでに保存された履歴を消す(考え方だけで、シミュレーションはしていません)。** 圧縮、要約、ツール結果のクリアは、戻ってメッセージ一覧にある履歴を消したり短くしたりします。ラボはどれもシミュレーションしていないので、ここからは考え方の計算だけです。すべてのリクエストに上限Wを付ければ、T(N) ≤ N·(F + W)となり、上限に達したあとはNに比例します。ラボの30回のリクエストの大きさに、リクエスト10の大きさで上限を付けると、こうなります。

```text
考え方だけで、ラボの結果ではありません: すべてのリクエストをR_10 = 17,747で上限を付ける
T = (R_1 + ... + R_10) + 20 × 17,747 = 98,386 + 354,940 = 453,326   上限なしの863,762と比べる
無視しているもの: 要約を作るトークン、書き換えのあとのキャッシュミス、失われる細部
```

実際のAPIがこれを提供しています。[Claudeのコンテキスト編集ドキュメント](https://platform.claude.com/docs/en/build-with-claude/context-editing#context-editing-and-prompt-caching)には、しきい値を超えた古いツール結果を消し、置き換えの文章に置き換える方法が書かれています。消すとキャッシュされた先頭部分が無効になるので、消すならトークンを十分に減らす価値がある量にしてください。編集すると、その編集を含むキャッシュされた先頭部分は再利用できなくなります。編集より前の、変わっていない先頭部分はまだ当たることがあります。残りは、キャッシュされていないか、キャッシュ書き込みの料金で課金されます。だから、入るときに切り詰めると先頭部分は安定したままでキャッシュにやさしく、履歴を書き換えると伸びに上限は付きますが、編集のあとの先頭部分は壊れます。

**消すのがいつ元を取るか。** ラボの例示のキャッシュ価格(読み取り0.30ドル、書き込み3.75ドル、100万トークンあたり)と、キャッシュがそのまま温かいと仮定します。古いツール出力C = 20,000トークンを消し、編集のあとにあってキャッシュされていたR = 10,000トークンをもう一度書き直すとします。

```text
あとの1回の呼び出しでの節約 = C × 読み取り       = 20,000 × 0.30 / 100万          = 0.0060ドル
1回だけの書き直しの罰      = R × (書き込み - 読み取り) = 10,000 × (3.75 - 0.30) / 100万 = 0.0345ドル
元を取るまでの呼び出し回数 = 0.0345 / 0.0060  = 5.75  → 6回めのあとの呼び出しから元が取れる
```

一般に、消した場所にsトークンの要約を残し、要約の呼び出しがC_sumかかるとすると、消すのがk回のあとの呼び出しで元を取るのは、こういうときです。

```text
k × (C - s) × 読み取り  >  R × (書き込み - 読み取り) + s × 書き込み + C_sum
```

大きくまとめて消し、編集は先頭部分のできるだけ後ろに置き(Rを小さく)、長い末尾の直前にやってください。キャッシュがなければ、1回の呼び出しでの節約はC × 入力価格で、消すのはほぼすぐに元が取れます。編集するときは、履歴を有効に保ってください。すべてのツール呼び出しには、それに対応する結果がまだ必要です(Claudeは`tool_use`と`tool_result`をIDで結び、OpenAIは関数呼び出しとその出力を`call_id`で結びます)。だから、ペアの片方を消すのではなく、結果の中身を置き換えの文章に置き換えてください。

## プロンプトキャッシュは何を変えて、何を変えないのか
このシリーズのパート33、キャッシュアサイドは「もっとも速いリクエストは、そもそもしないリクエスト」です。アプリはデータベースの前にキャッシュを見て、ミスしたら埋めます。プロンプトキャッシュは、同じ狙いにひねりを加えたものです。リクエストはやはり送られ、全文がモデルの入力のままですが、プロバイダーは最近見た先頭部分のキーと値のテンソルを再利用し、新しい末尾だけプリフィルします。[OpenAIのプロンプトキャッシュガイド](https://developers.openai.com/api/docs/guides/prompt-caching#what-is-the-prompt-cache)によれば、キャッシュが保存するのはKVテンソルであって、トークンそのものではありません。[プルCDN](https://systemdesignsimple.com/why-netflix-doesnt-buffer-in-kathmandu/)が、オリジンへ戻る代わりに保存されたコピーを出すのと同じ仕組みです。

公式ドキュメントから、仕組みはこうです。

- **先頭部分の完全一致。** ヒットするには、リクエストがキャッシュされたエントリとまったく同じトークンで始まる必要があります。Claudeのドキュメントでは、先頭部分はツール、システム、メッセージの順に作られ、あるレベルで変わると、そのレベルとそれ以降がすべて無効になります。OpenAIのドキュメントも同じことを言っています。変わる内容のあとに区切りを置き、変わらない内容を再利用できる先頭部分にしてください。
- **区切り、Claude。** `cache_control`がキャッシュの区切りを付けます。1回のリクエストに最大4つまでで、各区切りから最大20ブロックまで後ろを見ます。
- **Claudeの制限と価格。** キャッシュできる先頭部分の最小値は、モデルによって512から4,096トークンです。既定のエントリは5分間生き、使うたびに更新され、1時間の選択肢もあります。キャッシュ読み取りは、多くのモデルで基本の入力価格の0.1倍(安いものもあります)、5分の書き込みは1.25倍、1時間の書き込みは2倍です。使用量には`cache_creation_input_tokens`と`cache_read_input_tokens`が出ます。

OpenAIのガイドはモデルの世代を分けているので、下のルールは世代をまたいで同じではありません。

- **GPT-5.6以降。** 既定では暗黙のキャッシュで、明示モードでは`prompt_cache_breakpoint`をコンテンツブロックに付けます(1回のリクエストに最大4つのキャッシュ書き込み)。キャッシュできるプロンプトの最小値は1,024トークンです。既定の最小の寿命は30分で、Responses APIでは12時間の寿命を高い書き込み料金で頼めます。書き込みは、30分でキャッシュされていない入力料金の1.25倍、12時間で2.5倍です。読み取りは、ほとんどのモデルで0.1倍です。入力トークンはそれぞれ、キャッシュされていない、キャッシュされた、書き込みのいずれか1つの料金でちょうど課金されます。キャッシュされたトークンは、対象になる境界で正確に報告されます。使用量には`cached_tokens`(読み取りだけ)と`cache_write_tokens`があります。`prompt_cache_key`は任意で、別のキャッシュ会計に使います。
- **GPT-5.5以前。** キャッシュ書き込みの料金は別にありません。保持期間は`prompt_cache_retention`で決めます。メモリ内のエントリは、ふつうは使われないまま5から10分、最大で1時間残り、24時間の選択肢があるモデルでは、ふつうは30分ほど、最大で24時間残ります。キャッシュされたトークンは、128の倍数に切り捨てて報告されます。安定した`prompt_cache_key`があると、同じ先頭部分を共有するリクエストを同じキャッシュへ振り分ける助けになります。

使うモデルの現在のページで確かめてください。こうした細部は世代で変わります。

エージェントは、理想に近い仕事の形です。すべてのリクエストが、前のリクエストに小さな末尾を足したものだからです。ラボは、書き込みに割増のあるキャッシュ(Claude式で、GPT-5.6からのOpenAIも同じ)で価格を付けています。再送されるトークンはすべて入力の10%の読み取り価格で、新しいトークンはすべて一度だけ125%で書き込まれると仮定し、最小の大きさと有効期限は無視します。

```text
中くらい、30回、例示の価格(100万トークンあたりドル): 読み取り0.30、書き込み3.75、出力15
再送分  = 863,762 - 51,686 = 812,076 × 0.30 / 100万 = 0.2436ドル
新規分  =           51,686 ×  3.75 / 100万        = 0.1938ドル
出力                                              = 0.0358ドル
キャッシュありの合計 ≈ 0.4733ドル(ラボ)    キャッシュなしの合計 = 2.6271ドル(ラボ)
節約 = 1 - 0.4733 / 2.6271 = 82.0%
```

トークン数は863,762のままで、94.0%が再送で、伸びはN²に近いままです。キャッシュは履歴の項の価格を下げますが、その形とコンテキストウィンドウはそのままです。リクエスト50(中くらい)は、キャッシュがあってもなくても95,962トークンです。書き込みは0.25倍の割増で、1回の読み取りは0.9倍の節約になるので、先頭部分はもう一度読まれれば元が取れます。キャッシュがあっても、履歴の項は、新しい末尾に対するプリフィルが全文のコンテキストに対してかかり、KVメモリはリクエストの大きさで増えます。なくなるのは、先頭部分の繰り返しのプリフィルだけです。

## 失敗のパターン
**コンテキストウィンドウに当たる。** リクエストの大きさは線形に増えるので、長いタスクはいつかモデルのコンテキストウィンドウを超えて、呼び出しが失敗します。呼び出しごとにリクエストの大きさを記録し、制限の一部を超えたらアラートを出し、ツール出力の上限、コンテキストを新しくするサブタスク、圧縮で直します。Claudeのコンテキストウィンドウのページも、トークン数が増えると精度と想起が落ちると警告しています。収まるリクエストが、自動的に良いリクエストとは限りません。

**気づかないキャッシュミス。** システムプロンプトのタイムスタンプ、ツール定義のキーの順番の違い、タスクの途中でのツールの追加、早いメッセージの編集は、先頭部分を変えます。変更を含むキャッシュされた先頭部分は再利用できなくなります。変わっていない先頭部分はまだ当たることがありますが、それ以降はキャッシュされていないかキャッシュ書き込みの料金がかかります。システムプロンプトやツールの変更がいちばんひどいのは、その前にほとんど何もないからです。使用量の欄で、読み取りと書き込みの両方を見てください。Claudeは`cache_read_input_tokens`と`cache_creation_input_tokens`を、OpenAIは`cached_tokens`と、書き込み価格のあるモデルでは`cache_write_tokens`を報告します。健全な追加だけのループでは、読み取りは呼び出し番号とともに増え、書き込みは各新しい末尾の大きさに近くなります。連続する呼び出しで、書き込みがリクエスト全体の大きさに近いままだと、先頭部分が毎回変わっている証拠です。

**遅いステップのあいだのキャッシュ切れ。** TTLを超えるツール(長いテストスイート、人の承認)があると、再利用できる先頭部分がなくなり、次のリクエストは履歴全体を、プロバイダーとモデルによってキャッシュされていないかキャッシュ書き込みの料金で課金します。提供されているなら長いTTLを使い、その高い書き込み料金と、ステップが短いTTLを実際に超える頻度を比べてください。

**早い段階の1つの巨大なツール結果。** 呼び出し2でのフィルタなしのログは、その後のすべての呼び出しで送り直されます。ツール結果は、大きさに残りの呼び出し回数を掛けて順位を付け、ツールの側で直します。

**タスクではなく呼び出しごとの予算チェック。** 1回の呼び出しはどれも妥当に見えて、タスク全体はそうではありません。呼び出しごとに実行中の合計をタスクごとの予算と比べます。

**推論トークン。** ラボはシミュレーションしていません。APIが推論の項目を返してほしい場合、それらは履歴に入り、課金されます。

## よくある間違い
**間違い:** エージェントのコストを、呼び出し回数に1回の呼び出しの大きさを掛けて見積もること。**代わりに:** 階段を合計します。T(N) = N·F + a·N(N-1)/2です。ラボの30回では、最初のリクエストは2,230トークンですが、合計は863,762トークンです。

**間違い:** 「チャットの5,467倍」をコストとして引用すること。**代わりに:** どの倍率かを言います。読んだ倍率は5,467倍ですが、例示の価格でのコストの倍率は277倍です。チャットはほとんどが出力で、エージェントはほとんどが入力だからです。

**間違い:** プロンプトキャッシュがトークンを減らす、またはコンテキストの空きを増やすと思うこと。**代わりに:** 再利用される先頭部分の価格と処理が変わるだけです。モデルは同じ863,762トークンを読み、リクエストはやはりウィンドウに収まる必要があります。

**間違い:** プロンプトの先頭にタイムスタンプ、リクエストID、順不同のツール一覧を置くこと。**代わりに:** 先頭部分をバイト単位で安定させます。ツールとシステムを先に、並べ替えて固定し、変わるデータは最後に置き、使用量の欄でキャッシュされたトークン数を確認します。

**間違い:** 「ツール出力を切り詰める」と「履歴を圧縮する」を同じ修正だと思うこと。**代わりに:** 入るときに切り詰めると傾きが下がり、キャッシュは保たれます。圧縮は大きさに上限を付けますが、編集のあとの先頭部分のキャッシュ再利用を止めます。タスクの長さと元を取るまでの呼び出し回数で選んでください。

**間違い:** この見積もりや、リクエストJSONに対するトークナイザーの実行を、課金のデータとして使うこと。**代わりに:** APIはメッセージとツールをモデルごとの入力に変換します。呼び出し前にプロバイダーのトークン数え上げエンドポイントを使い、呼び出し後に返ってくる`usage`を使ってください。

**間違い:** 予算を呼び出しごとに決めること。**代わりに:** タスクごとにトークンの予算を決め、実行中の合計が超える前に止めるか、分割するか、圧縮します。

## 私たちの見解
モデルは呼び出しのあいだ何も覚えていません。追加だけのループでは、すべての呼び出しのコンテキストが、システムプロンプト、ツールスキーマ、それまでのすべてのメッセージとツール結果です。クライアントが送るか、プロバイダーが保存した状態から組み立てるかは、課金には関係ありません。リクエストの大きさは階段状に増え、増分がほぼ一定なら合計はN·F + a·N(N-1)/2、つまりN²に近づきます。私たちのラボでは、30回のタスクで合計863,762トークン、その94.0%が再送でした。読んだトークンではチャットの5,467倍ですが、コストでは277倍です。数字を引用するときは、どの倍率かを言わないと、話が1,000倍にも5,000倍にもなってしまいます。

直す順番は3つです。まず、ツール結果が履歴に入る前に小さくします。行の範囲、一致数の上限、失敗だけのテスト出力です。早い結果ほど、送り直される回数が多いので効きます。次に、先頭部分をバイト単位で安定させてプロンプトキャッシュを使います。再送されるトークンはキャッシュ読み取りの価格になり、私たちのラボでは例示のコストが82%下がりました。トークン数そのものは変わらないので、ウィンドウの心配は残ります。最後に、長いタスクでは、古いツール結果を消すか要約するか、サブタスクに分けます。消すのは、1回の呼び出しでの節約に残りの呼び出し回数を掛けたものが、キャッシュされた末尾を書き直すコストを上回るときです。私たちの例では、6回めのあとの呼び出しから元が取れました。追う指標は、タスクごとの入力の合計、キャッシュされた割合、もっとも大きいツール結果、リクエストの最大の大きさです。予算はタスクごとに決めてください。
